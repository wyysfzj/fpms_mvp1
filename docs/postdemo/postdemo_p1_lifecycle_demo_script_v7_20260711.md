# FPMS P1 七版客户演示主持人脚本

本文是 V7 现场主持脚本。它以一个现场创建的客户和一个现场创建的案件，展示七项 GAP
能力如何沿真实公开 UI/API 路径形成可观察的业务闭环。本文不替代产品规格，也不包含环境
搭建、数据清理或命令行操作；现场准备、证据目录和停止条件由配套运行手册负责。

## 一、演示口径与固定数据

### 1.1 开场话术

> 今天我们从新客户和新案件开始，沿同一案件展示递交准备、OA、回执、授权替换和费用
> 节点。每一步都同时复盘案件业务状态、法律状态、工作包/文件状态和费用节点状态。
> FPMS 管理的是准备、复核、归档和追踪；本次不承诺自动提交官方系统，也不承诺自动
> 签名、自动下载回执、自动缴费或自动发送邮件。

### 1.3 四类状态的唯一讲解词汇

| 状态维度 | 本脚本使用的状态链 |
| --- | --- |
| 案件业务状态 | 客户资料建立 → 新案立案 → 递交准备 → OA答复处理中 → 授权处理 → 年费监控 |
| 法律状态 | 未递交 → 等待受理 → 实审中 → 一通或二通阶段 → 实审中 → 已授权 → 维持有效 |
| 工作包/文件状态 | 未创建 → 已解析/待准备 → 待提交 → 待回执 → 已归档/已关闭；授权任务另分来源已确认/已被替代 |
| 费用节点状态 | 无费用 → 待预览 → 待客户指示 → 已生成草单 → 已生成官费清单 → 待缴费登记 → 已登记 |

打开或解析递交准备工作包，只能证明内部准备链路可达，不能证明已经向官方提交，也不能
单独推进法律状态。主持人必须以官方来文、有效回执或其他明确业务证据解释法律状态变化。

## 二、七项 GAP 现场处理矩阵

| ID | 现场动作 | 客户可观察检查点 |
| --- | --- | --- |
| `WIZARD` | 打开中间文件向导，使用有界的真实模板列表。 | 页面正常加载，不因模板请求过大而固定失败。 |
| `WORKPKG` | 对递交和 OA 分别执行 existing-first resolve，并重复进入。 | 重复进入复用同一工作包，真实页面可达且不依赖 enrichment。 |
| `OA` | 建立 `OA_OUT`，归档有效回执，再建立后续OA。 | 答复文书不提前关任务；后续OA有新的来源、工作包和任务身份。 |
| `RECEIPT` | 先演示错误案件、错误来源，再归档本案正确来源回执。 | 两种错误均失败且状态不变；有效回执只关闭一个 OA 任务。 |
| `CATALOG` | 展开官方通知目录。 | 60 行均可见；`可执行` 行可选，`仅供参考` 行不可执行。 |
| `DEADLINE` | 使用日期、来源、`CONFIRMED` 完整期限组，覆盖预览、创建、读取、更新和向导。 | 完整期限可回显；缺项、格式错误或冲突输入失败且不写入。 |
| `GRANT` | 建立来源已确认的授权任务、替代来源，再尝试操作旧任务。 | 首次不自动生成草单；旧任务显示已被替代且不可变更；新任务按客户缴费指示生成草单。 |

## 三、V7-01 至 V7-14 主持步骤

### V7-01：现场创建客户和主联系人

- 要做的内容：在客户页面现场创建客户，再进入客户详情新增主联系人。
- 输入的字段和值：按 1.2 冻结表完整填写客户和主联系人字段，不省略客户类型、币种、邮箱、
  联系人职务、手机、邮箱和主联系人标志。
- 点击的按钮：在“新建客户”页点击“保存”；进入“联系人”页签，点击“新增联系人”并
  “保存”。
- 期望结果：客户详情显示固定名称和代码，联系人列表显示 `钱七老师`，后续案件与信函
  有同一客户来源。
- 主持人话术：我们先建立客户事实和可复用联系人，不从预置案件开始。后续所有页面都
  回到同一个客户和同一个案件。
- 失败演示：用代码 `PD-P1-V7-LIVE` 再次新建客户，展示系统不接受重复业务标识；不把
  技术错误码作为客户讲解内容。
- 恢复方式：取消重复创建，搜索并回到刚才成功创建的客户详情，确认原记录未被覆盖。
- Evidence：`run-record.md#V7-01` 记录客户/联系人动态 ID；截图保存为
  `screenshots/V7-01-01-客户详情.png` 和 `screenshots/V7-01-02-主联系人.png`。
- 案件业务状态：客户资料建立。
- 法律状态：N/A（案件尚未创建，不使用“未递交”描述客户记录）。
- 工作包/文件状态：未创建。
- 费用节点状态：无费用。

- 主持人话术：案件由 UI 现场建立。此刻只是新案立案，尚未发生官方递交，也没有费用

### V7-04：递交准备 existing-first resolve 与真实页面可达

- 要做的内容：从案件进入“新申请递交准备”，重复进入一次，确认复用同一工作包。
- 输入的字段和值：使用案件 `P1E2E-V7-LIVE`，不输入或替换固定工作包 ID。
- 点击的按钮：点击“新申请递交准备”；返回案件后再次点击同一入口。
- 期望结果：两次进入均显示“新申请递交准备”，运行记录中的工作包 ID 相同；本步骤
  核心 GAP 路径不得使用 enrichment。
- 主持人话术：这是 existing-first resolve：没有时创建，已有时复用。页面可达表示内部
  准备链路成立，不表示官方已经收到申请。
- 失败演示：刷新页面或重复点击入口，证明不会生成第二个递交工作包；不演示伪造固定 ID。
- 恢复方式：保留首次生成的工作包，回到其真实页面继续；如页面未加载则停止本轮核心链路，
  由运行人员按运行手册排查，不能用 enrichment 补造。
- Evidence：`run-record.md#V7-04` 记录两次 resolve 的同一动态 package ID；
  `screenshots/V7-04-01-递交准备页.png` 保存页面与“未递交”状态。
- 案件业务状态：新案立案 → 递交准备。
- 法律状态：未递交（人工官方提交及证据完成后才可讲等待受理）。
- 工作包/文件状态：已解析/待准备 → 待提交。
- 费用节点状态：待预览。

- 要做的内容：登记第一次审查意见通知书，填写完整官方期限组，执行影响预览、保存、
  读取和一次更新，再进入 OA 答复工作包。
- 输入的字段和值：模板“第一次审查意见通知书”；收文方向“来文”；文书日期
  `2026-07-11`；官方截止日 `2026-10-15`；来源选择“人工录入官方通知”；确认状态
  “已确认”（`CONFIRMED`）。更新时仅将说明改为“V7 现场已复核”，期限组保持不变。另用
  `CLIENT_IN` 普通来文模板、方向“来文”、日期 `2026-07-13`、截止日 `2026-12-15`、来源
  “导入官方通知”和“已确认”完成期限向导创建验证，不解析核心工作包。
- 点击的按钮：点击“影响预览”“保存”；进入文书详情核对期限；点击“编辑”“保存”；
  点击“进入 OA 答复工作包”，并重复进入一次。
- 期望结果：创建、读取、更新和预览均显示同一日期/来源/已确认状态；同一来源重复解析
  复用同一 OA 工作包；页面标题显示“OA答复工作包”。
- 主持人话术：第一次 OA 由明确官文和已确认期限推动。工作包绑定这份来源文书，重复
  进入不会复制任务。本步只观察到 OA 官方通知及其对应阶段，不把未现场证明的“等待受理”
  或先前“实审中”转换讲成系统刚刚完成。
- 失败演示：清空期限来源或确认状态后尝试预览/保存，展示系统拒绝不完整期限；记录仍
  保持上次已确认值。
- 恢复方式：恢复日期、来源和已确认状态，重新预览；只对已成功创建的来源文书进入工作包。
- Evidence：`run-record.md#V7-05` 记录首次 OA source/package/task ID 与期限三元组；截图保存
  为 `screenshots/V7-05-01-OA期限.png` 和 `V7-05-02-OA工作包.png`。
- 案件业务状态：递交准备 → OA答复处理中。
- 法律状态：一通或二通阶段（由本步 OA 官方通知直接证明；不叙述未观察的前序转换）。
- 工作包/文件状态：已解析/待准备 → 待提交。
- 费用节点状态：待预览（常规 OA 不自动生成官费草单）。

### V7-06：创建 OA_OUT 并证明任务和案件仍保持打开

- 失败演示：在没有有效回执时尝试“归档”，展示硬门禁不通过；不以错误码作主要话术。
- 恢复方式：返回工作包，保持任务打开，继续 V7-07 和 V7-08 的回执验证。

- 法律状态：一通或二通阶段。
- 工作包/文件状态：待提交 → 待回执。
- 费用节点状态：待预览。

### V7-07：现场构造并演示错误案件与错误来源回执均失败

- 要做的内容：本步通过真实公开 UI/API 行为现场创建一个隔离的错误案件，在该案文书下上传
  一份电子申请回执；再在 V7 主案件中创建一份与首次 OA 答复链无关的普通发文并上传第二份
  电子申请回执。捕获两份文书和附件的动态 ID 后，依次向首次 OA 工作包提交错案回执和同案
  错来源回执。不得使用 enrichment、历史预置记录或直接数据库写入。
- 输入的字段和值：错误案件使用案号 `P1E2E-V7-RECEIPT-GATE-<运行后缀>`、标题“V7回执
  归属门禁隔离案件”、V7 客户、普通案件、发明、中国国内、未递交。两份载体均冻结为
  `doc_template_id=null`（无模板）、业务类型 `CLIENT_OUT`、方向 `OUT`、日期 `2026-07-12`；
  标题分别为“V7跨案回执载体”和“V7同案非OA来源文书”。两份附件角色均为
  `ELECTRONIC_RECEIPT`。两轮回执元数据均完整填写接收案号、提交人、接收时间和收到文件清单。
- 点击的按钮：两份载体统一使用已验证公共入口 `POST /api/v1/documents` 创建，再使用
  `POST /api/v1/documents/{document_id}/attachments` 上传附件；动态 ID 写入运行记录。回到
  首次 OA 工作包，通过公共回执登记动作分别提交两份附件。页面只用于展示中文失败结果。
- 期望结果：两次均显示中文业务提示并失败；OA 任务仍打开，工作包未归档，案件仍处于
  一通或二通阶段，既有数据无 mutation。
- 主持人话术：回执不仅要“有文件”，还必须属于当前案件和当前 OA 来源链。错误归属不会
  悄悄改变任务或案件。
- 失败演示：本步骤本身即失败演示；只讲“回执不属于当前案件”与“回执不属于当前来源”，
  不展示内部错误代码作为客户主叙事。
- 恢复方式：保留两次失败的无变更证据，在运行记录中把隔离案件、普通发文和两份附件标为
  本轮可定向清理对象；清空错误附件选择后进入 V7-08，不复用这些附件走成功路径。
- Evidence：`run-record.md#V7-07` 记录隔离案件、跨案文书/附件、同案非来源文书/附件的动态
  ID 和真实创建入口；`screenshots/V7-07-01-错案回执无变更.png`、

## 五、演示成功标准

1. V7-01 至 V7-14 均有现场结果，并与配套运行手册的同名检查点一一对应。
2. 客户能从页面辨认同一个客户和案件，并能复述四类状态的变化依据。
3. 七项 GAP 的成功与失败路径均由可观察状态证明，不能只靠主持人口头说明。
4. 首次 OA 只有在有效自有回执归档后关闭；后续OA保留独立身份，并在进入授权前由其自身
   的有效自有回执完成闭环。
5. 授权任务首次不自动生成草单；替代后旧任务不可变更，新任务按客户 PAY 指示走正常草单路径。
6. 任何核心 GAP 路径不得使用 enrichment；当前缺少 V7-safe enrichment/cleanup，V7-13 与
   整体 READY 必须保持 `BLOCKED`，直至独立原子任务补齐前置。
