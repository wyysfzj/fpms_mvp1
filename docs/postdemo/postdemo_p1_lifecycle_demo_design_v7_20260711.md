# 第一阶段专利案件全流程 V7 演示设计

## 一、文档定位

本文档定义 V7 客户演示的业务含义和能力边界。演示仍以一个国内发明专利案件贯穿客户建档、新案立案、递交准备、审查意见答复、授权处理和年费监控，但重点是说明已闭合的七项 GAP 如何由真实业务对象、来源文件、期限、任务和回执共同约束。

本文档只定义“演示什么、业务上代表什么、怎样才算成功”。逐步按钮、主持人话术、环境准备、故障恢复和清理命令分别由 V7 脚本和运行手册负责。

## 二、设计目标

V7 应让客户清楚理解：

1. 客户和案件由业务人员在 UI 中现场创建，同一案件沿一条生命周期连续推进。
2. 案件业务状态、法律状态、工作包/文件状态、费用节点状态是四个不同维度，不能互相代替。
3. 准备包可打开或已解析，只表示内部准备工作可继续，不等于已经向官方系统提交，也不构成法律状态推进证据。
4. OA 的关闭必须以归属于同案、指向正确 OA 来源且元数据完整的官方回执成功归档为证据。
5. 授权费用任务必须能够追溯到已确认来源；客户尚未给出缴费指示时，不提前产生费用草单。
6. 失败场景采用“拒绝并保持原状”的方式展示，不能靠人工口头修改状态完成闭环。

## 四、四类状态的统一含义

四类状态必须分别展示并说明证据来源。任何一步都不得用“页面打开成功”代替状态变化，也不得用内部准备状态推断官方法律状态。

| 状态维度 | V7 允许使用的状态主线 | 业务含义 |
| --- | --- | --- |
| 案件业务状态 | 客户资料建立 → 新案立案 → 递交准备 → OA答复处理中 → 授权处理 → 年费监控 | 事务所内部正在处理的业务阶段。 |
| 法律状态 | 未递交 → 等待受理 → 实审中 → 一通或二通阶段 → 实审中 → 已授权 → 维持有效 | 由官方递交、来文、回执和授权等证据支持的法律生命周期。 |
| 工作包/文件状态 | 未创建 → 已解析/待准备 → 待提交 → 待回执 → 已归档/已关闭；授权任务另分来源已确认/已被替代 | 文件与任务是否已准备、是否等待官方回执、是否有资格继续操作。 |
| 费用节点状态 | 无费用 → 待预览 → 待客户指示 → 已生成草单 → 已生成官费清单 → 待缴费登记 → 已登记 | 费用从预览、客户决策到人工缴费登记的内部进度。 |

解析或打开递交准备包、OA 答复包，只改变案件业务状态或工作包/文件状态。没有官方提交或回执证据时，法律状态不得因此前移。费用预览、草单或清单也不表示已经自动缴费。

## 五、单案生命周期设计

| 生命周期阶段 | 真实业务证据与动作 | 四类状态的关键变化 | 客户应看到的结果 |
| --- | --- | --- | --- |
| 客户与案件建立 | 在 UI 创建冻结客户、主联系人和案件 | 案件业务状态进入“客户资料建立、新案立案”；法律状态为“未递交”；工作包“未创建”；费用为“无费用” | 本轮不是预置或复用旧案，后续对象都归属于同一案件。 |
| 递交准备 | 通过 existing-first 方式解析或复用同案递交包 | 业务进入“递交准备”；工作包进入“已解析/待准备、待提交”；法律状态仍为“未递交” | 真实页面无需 enrichment 即可到达；准备完成不等于官方递交。 |
| 受理与实审 | 由官方提交/受理证据推动 | 法律状态由“等待受理”进入“实审中”；费用可进入“待预览” | 状态、文件和费用节点具有可解释的业务来源。 |
| OA 来文 | 创建带完整官方期限的 OA 通知并解析同源工作包 | 业务进入“OA答复处理中”；法律状态进入“一通或二通阶段”；工作包待准备/待提交 | OA 来源、期限、工作包和任务能够对应。 |
| OA 答复与回执 | 创建 OA_OUT；先验证错误回执，再归档同案正确来源回执 | OA_OUT 后任务仍开放且案件仍处于 OA；有效回执归档后恰好一个任务关闭、案件回到“实审中” | 内部答复文件不是关闭证据，官方回执才是硬门禁。 |
| 后续 OA | 同一案件创建另一份 OA 来文 | 新 OA 拥有不同的来源、工作包和任务身份 | 历史 OA 不会被复用或误关闭。 |
| 授权通知 | 创建带完整官方期限的授权通知 | 业务进入“授权处理”；法律状态保持此前实际观察值；授权任务“来源已确认”；费用“待客户指示” | 通知只证明期限、来源血缘和任务行为；只有另一个真实公开案件状态动作或官方证据才能记录“已授权”，且不自动生成草单。 |
| 授权替换与客户指示 | 用新授权来源替换旧来源，随后只在新任务上接收客户缴费指示 | 旧任务“已被替代”，新任务“来源已确认”；旧任务操作被禁用，新任务按正常 PAY 路径生成草单 | 替换谱系清楚，旧任务不可继续变更，客户指示才触发费用草单。 |
| 年费监控 | 使用演示支持数据展示年费任务、预览与清单 | 仅展示年费 fixture 时，案件业务状态保持“授权处理”、法律状态保持此前实际观察值；费用按实际证据推进 | “年费监控”需要独立的真实公开行为/证据；若此前没有单独证据建立“已授权”则不得补讲，只有实际缴费登记或官方状态证据才能支持“维持有效”。 |

## 六、七项 GAP 规范矩阵

下表中的 canonical ID 是三份 V7 文档共同使用的校验标识；面向客户讲解时以右侧中文业务含义为主。

| Canonical ID | V7 设计处理 | 成功证据与失败边界 |
| --- | --- | --- |
| `WIZARD` | 文书向导使用有上限的真实模板列表。 | 正常列出可用模板，不再因确定性的分页尺寸超限产生 422；不以 mock 列表代替真实请求。 |
| `WORKPKG` | 新申请和 OA 都采用 existing-first resolve：同一来源已有工作包就复用，没有才创建。 | 无需 enrichment 即可到达真实递交准备页和 OA 答复页；打开工作包不代表已官方提交。 |
| `OA` | OA 来源键决定工作包和任务身份；创建 OA_OUT 只记录内部答复输出。 | OA_OUT 后任务保持开放、案件保持 OA 状态；后续 OA 必须有不同来源、工作包和任务身份。 |
| `RECEIPT` | 归档前同时校验同案关系、OA 来源归属、完整元数据，并在归档事务中再次确认。 | 错案或错误来源回执失败且不发生任何状态变更；归档同案且正确来源的有效回执后，只关闭恰好一个 OA 任务并恢复案件。 |
| `CATALOG` | 官方通知目录完整展示 60 行，并以中文区分“可执行”和“仅供参考”。 | 已批准行可执行；参考行禁用且不能触发自动化，未确认分类按不可执行处理。 |
| `DEADLINE` | 每份可执行 OA 或授权通知都携带明确的“日期、来源、`CONFIRMED`”三元组，并贯穿创建、读取、更新、向导和影响预览。 | 页面显示日期、来源和“已确认”；缺失、格式错误、不完整或冲突输入都失败并保持原状。 |
| `GRANT` | 授权通知创建与来源相连的已确认任务；替换动作原子生成新任务并保留新旧谱系。 | 初始任务不自动生成草单；旧任务标为“已被替代”，直接草单、批量指示、通知生成及状态变更均失败，UI 操作禁用或隐藏；新任务收到客户 PAY 指示后走正常草单路径。 |

文书创建及其必需的工作包、期限或任务副作用必须保持原子性：要么全部成功，要么全部不落库，不能留下半成品状态。

## 七、关键业务语义

### 7.1 OA 与回执

- 可执行 OA 来文必须在创建时提供官方期限日期、期限来源和 `CONFIRMED` 状态；系统不得猜测或用缺省值补齐。
- 创建 OA_OUT 不会关闭 OA 任务，也不会让案件从“一通或二通阶段”回到“实审中”。它只证明内部答复文件已经形成。
- 回执必须与 OA 任务同案，并指向该任务的正确 OA 来源。错误案件、错误来源、元数据不完整或归档事务失败时，文件、任务和案件均保持原状。
- 只有有效回执成功归档，才关闭恰好一个 OA 任务并恢复案件。后续 OA 必须新建独立身份，不能覆盖或复用历史任务。

### 7.2 期限

期限不是一段备注文字，而是由日期、来源和确认状态组成的结构化业务事实。创建、查看、编辑、文书向导和影响预览必须读取同一事实；任何缺失、畸形、不完整或冲突输入都采用 fail-closed，即拒绝操作且不产生副作用。

面向客户只展示“期限日期、依据来源、已确认”等中文业务信息；`CONFIRMED` 仅作为文档内的技术校验词，不作为主讲术语。

### 7.3 授权与费用

- 授权通知必须有明确期限三元组，并创建与该通知来源相连的确认任务。
- 授权通知或授权任务的创建本身不推进案件法律状态；“已授权”只能来自另一个真实公开案件
  状态动作或官方证据，并记录其实际观察结果。
- 任务创建时“不自动生成草单”。客户缴费指示是进入正常费用草单路径的必要业务动作。
- 更正或替换授权通知时，新来源生成新的确认任务，旧任务保留历史并标记为“已被替代”。
- 旧任务的直接草单、批量客户指示、通知生成和状态变更都必须被阻止，页面相应入口禁用或隐藏。
- 新任务仍遵循正常路径：客户给出 PAY 指示后，才生成草单并继续官费清单与人工缴费登记。

## 八、真实路径与 enrichment 边界

V7 采用“核心能力走真实路径、少量外围演示数据后置补齐”的混合策略。

必须使用真实公开 UI/API 行为、且不得使用路由 mock、直接数据库写入或 enrichment 的核心路径包括：

- `WIZARD` 文书向导和 `CATALOG` 60 行目录分类；
- `WORKPKG` 新申请/OA existing-first resolve；
- `DEADLINE` 结构化期限；
- `OA`、`RECEIPT` 的来源归属、回执归档和后续 OA 身份；
- `GRANT` 的来源谱系、替换和不可变更门禁。

最小后置 enrichment 仅允许补齐当前 UI 无法在实用演示时长内端到端创建的三类外围 fixture：申请费、格式函和年费。每次使用都必须记录具体创建对象，明确说明这是演示支持而非生产业务行为，并同时满足：

1. 只在 UI 已创建客户和案件之后执行；
2. 不创建、覆盖或改写 UI 创建的客户、联系人和案件事实；
3. 不创建、覆盖或改写任何核心 GAP 对象；
4. 不以 enrichment 结果冒充真实路径通过证据。

年费 enrichment 只提供任务、预览和清单等外围展示记录，不得修改案件业务状态或法律状态。
若现场只有这些年费 fixture，案件业务状态必须保持“授权处理”、法律状态必须保持此前实际
观察值；只有独立的真实公开行为/证据才能把“年费监控”作为已发生的案件业务状态展示。若
此前没有单独证据建立“已授权”则不得补讲；只有实际缴费登记或官方状态证据才能把“维持有效”
作为已发生的法律状态展示。

## 九、客户沟通与能力边界

演示页面、状态和主讲口径使用简体中文业务语言。内部 ID、枚举、错误码和测试实现只用于演示记录或操作人员排障，不作为客户叙事主线。

V7 明确不承诺：

- 不承诺自动登录、自动提交或直接对接官方系统；
- 不承诺 RPA、自动扫码签名或自动下载官方回执；
- 不承诺自动缴费或完全替代官方缴费模板；
- 不承诺自动发送电子邮件；
- 不把路由 mock、数据库注入、enrichment 或人工改状态描述成生产能力；
- 不把准备包已解析、可打开或待提交描述成官方已接收；
- 不把费用草单、官费清单描述成已经完成官方缴费。

正确口径是：系统准备并核对业务字段和文件，依据明确来源管理任务与期限，以回执和官方来文作为状态证据，形成内部费用节点并保留审计关系；最终官方提交、签名、缴费和外部发送仍由人员或外部系统完成。

## 十、成功标准

V7 设计达到预期，需要同时满足：

1. 客户能识别同一个新客户、新联系人和新案件，并能说清四类状态各自代表什么。
2. 文书向导真实模板列表有界，官方通知目录 60 行全部可见，“可执行”与“仅供参考”清晰且参考行不可操作。
3. 新申请和 OA 工作包可通过真实 existing-first 路径到达，且不会被误讲为已经官方提交。
4. 每个可执行 OA/授权来源均显示明确日期、来源和“已确认”；不完整或冲突数据被拒绝且无副作用。
5. OA_OUT 后任务和案件仍处于 OA；错误案件/错误来源回执失败且不改变数据；有效同案正确来源回执只关闭一个任务；后续 OA 身份独立。
6. 授权任务与来源相连且初始没有草单；其创建不自动推进案件法律状态；替换后新旧谱系可见，旧任务不能继续操作，新任务只在客户 PAY 指示后生成草单。
7. 核心七项 GAP 全部由真实路径证明，enrichment 只覆盖申请费、格式函和年费外围 fixture，且有清晰记录；年费 fixture 不改变案件业务状态或法律状态。
8. 全程不承诺自动提交、自动签名、自动回执下载、自动缴费或自动邮件发送，也不把内部准备状态当作法律事实。
