## 1. 结论摘要

客户核心诉求不是“另起一套流程”，而是减少现有业务完成后在专利业务办理系统/CPC 客户端、OA 答复页面、邮件/信函系统中的重复录入、重复上传和格式修复。

建议将 enhancement 定位为：

1. MVP：建设“OA 答复工作包 + 人工审核提交”能力。系统在内部流程完成后，自动汇总申请号、申请人、官文、答复期限、意见陈述、修改文件、PDF 证明文件、操作清单和归档字段；人工仍负责在专利业务办理系统中最终预览、扫码签名、提交。
2. P1：基于官方 XML 数据标准和批量接口，生成可导入专利业务办理系统客户端的数据包或文件包，优先解决新申请递交、补正/OA 答复中的文件和表单重复录入。
3. P2：在获得官方接口或客户书面合规确认前，不承诺“网页登录后自动签名提交”。网页登录/RPA 自动操作存在稳定性、账号安全和服务协议风险。
4. 信函生成不是当前最大缺口。客户已有“龙虾”邮件自动发送系统且可用，现系统应先补齐格式函生成、命名规则、联系人抬头和归档/交接，而不是立即替换邮件发送。

现有系统已经具备可复用底座：案件、申请文件、文书模板、文书向导、OA 来文/答复链、任务生成、费用草单、附件上传、邮寄登记等。但它目前主要是“内部文书与任务管理”，不是“官方递交客户端自动化”。最大 GAP 集中在：官方提交包生成、富文本/公式/表格/图片保真、客户流程字段完整性、回执归档闭环、CPC/专利业务办理系统导入能力。

## 2. 客户流程分析：相关流程操作

### 2.1 新建案件流程

客户现行新建案件需要录入：

- 内部案号、申请人案号。
- 发明名称、专利类型：发明、实用新型、外观设计。
- 申请方向。
- 申请人：名称、国籍、地址、证件类型及号码、邮政编码、法人或自然人。
- 发明人：姓名、国籍；中国籍发明人需要身份证号。
- 技术交底书。
- 委托指示。

现有系统已有案件主表、申请人、发明人、优先权、PCT、费减、代理人/撰稿人等基础字段，例如 `backend/app/modules/cases/models.py` 中的 `Case`、`T_CaseApplicant`、`T_CaseInventor`。但对客户流程而言仍有字段缺口：

- 案件申请人缺少国籍、证件类型、证件号码、邮政编码等递交必需字段。
- 发明人缺少国籍和身份证号。
- 客户总委号、代理助理、递交请求书勾选项、官方客户端导入后仍需手填的字段，没有形成稳定的提交包字段。

Enhancement 方向：不应先重构案件模块，而应新增“递交准备/官方提交包”视角，把必填字段缺口作为提交前校验和补录项。

### 2.2 新申请递交流程

客户当前路径：

1. 在内部系统中通过案号找到案件。
2. 在“申请文件管理”上传完整 Word 递交文件，包括摘要、权利要求书、说明书、说明书附图、序列表等。
3. 补录或更新发明名称、代理人、撰稿人、代理助理、页数、权利要求项数、附图幅数、费减比例。
4. 使用天下先导出到 CPC 接口。
5. 在专利业务办理系统中选择“接收类表格导入”。
6. 进入新申请页面后继续人工补录部分字段，例如客户总委号。
7. 上传已转换为 XML 格式的压缩包，系统自动识别分配到摘要、权利要求书、说明书、附图。
8. 预览 PDF、人工核对、扫码提交。
9. 将提交后的合并 PDF 回传到内部申请文件管理归档。

现有系统已有“案件批件递交”候选与材料 gate：`frontend/src/modules/cases/pages/CaseBatchFiling.vue`、`backend/app/modules/cases/document_gate_service.py`。但该能力当前更像内部批件状态流转和材料完整性检查，不是官方接收类表格、XML 包、CPC/专利业务办理系统客户端导入包生成。

Enhancement 方向：

- MVP：生成“新申请递交工作包”：字段校验、文件清单、缺失项、操作清单、归档入口。
- P1：按官方数据标准生成可导入客户端的请求类表格 XML 数据包，并与 Word 转 XML 后的申请文件压缩包建立关联。
- P2：研究客户端批量接口的数据库/SQL 数据交换方式是否可被客户部署环境接受。

### 2.3 后续官文与 OA 答复流程

客户官文流程覆盖受理、申请费、补正、公布、实审、一通/二通/N 通、驳回、复审、授权、年费等。客户明确指出，所有“致函官方”文件目前只能在内部系统归档，不能从内部系统导入专利业务办理系统；必须在线填写、复制修改文件内容或上传 XML 文件。

这说明 enhancement 的主线应是“致函官方文件出站能力”，尤其是：

- 补正答复。
- 一通/二通/N 通意见陈述。
- 主动补正。
- 复审请求及复审意见陈述。
- 实审请求、费用减缓请求、PPH 请求等。

现有系统的 `DocTemplate`、`Document`、`reply_to_id`、`need_reply`、`TaskGenerationService` 已经能表达 OA 来文、答复任务、答复链和状态恢复。缺口在于“生成可提交内容”和“外部提交回执归档”。

### 2.4 缴费流程

客户缴费流程为：费用草单、官费缴费清单、官方 Excel 模板、专利业务办理系统网页批量号单上传、缴费人信息、预览并支付或稍后支付。

现有系统已有费用草单、费用项、官费清单、年费任务等基础能力。客户 post-demo 反馈中缴费不是本次最高优先级，但它影响 OA/授权后的工作包闭环。

Enhancement 方向：

- 保持缴费增强为后续阶段。
- 先保证 OA 答复、补正、授权相关文书能产生费用草单和操作提醒。
- 不在本次 MVP 中承诺自动支付或网页自动付款。

## 3. 客户流程分析：OA 答复流程

客户 OA 答复当前步骤：

1. 在“通知书办理”-“云端二次下载”中输入申请号，下载需答复官文。
2. 返回首页，进入“意见陈述/补正”。
3. 点击“答复审查意见”，按申请号查询未答复官文。
4. 点击“业务办理”。
5. 人工填写申请人、陈述的意见、附加文件。
6. 将意见陈述书内容复制到“陈述的意见”。
7. 公式、符号、表格、图片无法复制时，将文件转 PDF 作为其他证明文件上传，并在意见栏说明。
8. 保存、预览、检查、扫码签名、提交。
9. 在未确认列表批量接收确认，扫码下载电子申请回执。
10. 在已确认列表下载回执 PDF。

客户痛点很明确：

- 上传修改文件重复操作。
- 意见陈述重复复制粘贴。
- 复杂公式、符号、表格、图片无法可靠复制，需人工修复。
- 提交后回执仍需人工下载并回传归档。

MVP 不应直接替代人工签名提交，而应先把人工操作压缩为一次“工作包复核”：

- 自动生成可复制的纯文本意见陈述。
- 自动生成保留格式的 PDF 附件。
- 自动关联修改后的权利要求书、说明书、修改对照页等文件。
- 形成“申请人/申请号/官文/答复文件/附加文件/说明文字/待上传项/待下载回执”清单。
- 提交完成后提供回执 PDF 上传归档入口，关闭内部 reply task。

## 4. 客户流程分析：信函生成操作

客户现行信函流程：

1. 从“案件查询”进入案件“中间文件”。
2. 根据最新官方通知名称选择对应“格式函”。
3. 点击制作生成 Word 文件。
4. 按“我方案号-给申请人名称的邮件”命名，例如 `23F0207CN-给中国辐射防护研究院的邮件`。
5. 默认抬头为“尊敬的：您好”。
6. 如果天下先标记了客户联系人，抬头显示具体联系人，例如“尊敬的杨彪先生”。

客户已有“龙虾”邮件自动发送系统，且反馈“目前用着也还行”。因此本系统短期不应投入大量成本替换邮件发送，而应先把上游信函生成标准化：

- 官方通知到格式函的映射。
- 客户联系人抬头规则。
- 文件命名规则。
- Word 生成和归档。
- 对外邮件系统的交接清单或导出数据。

现有系统已有模板和文书渲染底座：`docxtpl` 渲染 DOCX、文书向导附件生成、文书邮寄登记。但模板上传、格式函映射、客户联系人规则、邮件系统对接仍需增强。

## 7. 推荐 MVP Enhancement 范围

MVP 应定义为“减少 OA 答复重复工作，并保证人工复核提交的可控闭环”。

### 7.1 MVP 关闭范围

- OA 答复准备页或工作包视图。
- 从 OA 来文文书进入答复工作包。
- 自动带出案件、申请号、申请人、客户、官文名称、官文代码、官方期限、内部期限。
- 上传/选择代理人完成的意见陈述 Word、修改后的权利要求书、修改对照页、其他附加文件。
- 从 Word 生成：
  - 可复制到网页字段的纯文本意见。
  - 格式保真的 PDF 附件。
  - 操作员检查清单。
- 记录人工审核状态。
- 记录外部提交状态：待准备、待复核、待提交、已提交、已回执、已归档。
- 提供电子申请回执 PDF 上传归档入口。
- 自动关闭或关联内部 OA 答复任务。

### 7.2 MVP 不关闭范围

- 自动登录专利业务办理系统。
- 自动扫码签名。
- 自动点击最终提交。
- 自动支付官费。
- 替换龙虾邮件发送系统。
- 完整实现所有官方表格 XML 数据标准。
- 保证所有 Word 公式可无损转为网页富文本。

这个边界更符合客户的真实痛点：工作已完成后，不希望重复劳动；但专利代理业务的最终提交仍需要人工核对和签名责任。

## 8. 目标业务流程设计

### 8.1 OA 答复工作包流程

1. 操作员登记或导入 OA 来文，系统生成 OA 答复任务。
2. 代理人完成意见陈述和修改文件。
3. 操作员在系统中打开“生成 OA 答复工作包”。
4. 系统自动检查：
   - 申请号是否存在。
   - 申请人是否完整。
   - 回复来源官文是否已选择。
   - 答复期限是否存在。
   - 修改文件是否齐全。
   - 意见陈述 Word 是否存在。
5. 系统生成：
   - `statement.txt`：用于粘贴到“陈述的意见”字段。
   - `statement.pdf`：用于保留公式、表格、图片。
   - `attachments/`：权利要求书、说明书修改页、对照页、证明文件。
   - `manifest.json`：文件角色、来源、哈希、操作提示。
   - `checklist.md` 或页面清单：人工提交步骤。
6. 人工在专利业务办理系统中上传/粘贴/预览/签名/提交。
7. 人工下载电子申请回执并上传系统。
8. 系统标记工作包已归档，关闭内部 OA 答复任务。

### 8.2 新申请递交工作包流程

1. 在案件批件递交页面选择案件。
2. 系统检查申请人、发明人、代理人、费减、页数、权利要求项数、附图幅数、申请文件是否完整。
3. 系统生成递交工作包：
   - 请求书字段清单。
   - XML 压缩包或待上传文件清单。
   - 专利业务办理系统操作清单。
   - 归档项：提交合并 PDF、电子申请回执。
4. P1 阶段再生成可导入客户端的请求类表格 XML 数据包。

### 8.3 信函生成流程

1. 官文入库后，系统根据官文代码/名称匹配格式函。
2. 选择客户联系人，生成抬头。
3. 按规则生成 Word 文件名：`{内部案号}-给{申请人名称}的邮件.docx`。
4. 文件归档到对应文书。
5. 输出给龙虾系统或邮件发送系统的交接数据。

### 9.4 字段与模板细节复核补充

二次复核后，建议在后续合同/PRD 中把字段和模板拆得更细：

1. 申请人字段：
   - 官方提交字段：名称、国籍、地址、证件类型、证件号码、邮政编码、法人/自然人类型。
   - 当前主数据/案件承载：`Applicant` 有编码、名称、类型；`T_CaseApplicant` 有名称和地址；`ClientAddress` 有 `postal_code`，但它是客户邮寄地址，不等同于官方申请人邮编。
   - GAP：申请人国籍、证件类型/号码、官方提交邮编需要补录或新增提交包字段。
2. 发明人字段：
   - 官方提交字段：姓名、国籍，中国籍需身份证号。
   - 当前承载：`T_CaseInventor` 仅有中英文姓名。
   - GAP：发明人国籍、身份证号至少要在递交工作包中作为必检项。
3. 代理与委托字段：
   - 客户流程明确提到代理人资格证号可由旧系统带入、客户有总委号仍需人工添加。
   - 当前案件有 `primary_agent_id`、`second_agent_id`、`draftor_id`，但未发现代理人资格证号、代理助理、客户总委号的稳定提交包字段。
   - GAP：新申请/OA 工作包应至少暴露“代理人资格证号来源”和“总委号是否存在”的检查结果。
4. 模板源字段：
   - 当前文书附件生成依赖 `DocTemplate.code` 与 `Template.name` 的约定匹配，并要求 `Template.group == "DOC_TEMPLATE"`。
   - 前端“上传模板”目前登记 `uploads/templates/{filename}` 路径，不能单独证明真实模板文件已上传到后端存储。
   - GAP：格式函和 OA 工作包附件生成前，应增加模板源存在性检查，避免只配了 `DocTemplate` 却没有可渲染 DOCX。
5. rate / fee 字段：
   - 当前 `FeeRate` 已可表达官方/服务费率、计算参数、是否允许费减、生效区间；申请费生成会读取 `fee_reduction` 和 `discount_rate`。
   - 客户缴费流程还要求“补充缴费信息模板”、官网“批量号单上传”、缴费人信息、订单支付/稍后支付。
   - GAP：系统已有 rate 和 pay-list 基础，但需要单独验证官方缴费 Excel 模板字段，而不是把内部 xlsx 导出等同于官网上传模板。

## 10. OA / CPC 对接方案

### 10.1 官方资料结论

根据国家知识产权局 2025-11-12 通知，自 2026-01-01 起，以电子形式办理专利申请、复审请求、无效宣告请求及相关手续，应以 XML 格式提交专利电子文件；范围包括请求类、意见陈述、补正等文件。通知同时要求当事人和代理机构履行文件核对义务。

专利业务办理系统“工具下载”中提供“专利电子申请数据标准规范及批量接口”。其中数据标准用于规范请求类表格 XML，批量接口包含业务数据表结构和 SQL，可与专利业务办理系统客户端进行数据交换。

专利业务办理系统用户服务协议对未授权第三方工具、插件、外挂、服务接入、干扰组件或数据等行为设置限制。因此，网页登录/RPA 自动提交不能作为默认 MVP 承诺，除非客户确认合规边界或取得官方授权。

参考来源：

- 国家知识产权局：《国家知识产权局关于全面实施以可扩展标记语言格式提交专利电子文件相关事宜的通知》：https://www.cnipa.gov.cn/art/2025/11/12/art_75_202551.html
- 专利业务办理系统工具下载：《专利电子申请数据标准规范及批量接口》：https://cponline.cnipa.gov.cn/GzfwYwblGlwhTMVC/GzfwYwblGlwhT/selectToolsById?weihuRid=248
- 专利业务办理系统用户服务协议：https://resources.cponline.cnipa.gov.cn/protocol/private/index.html
- 国家知识产权局：《国家知识产权局关于进一步推广使用可扩展标记语言（XML）格式提交专利电子申请文件的通知》：https://www.cnipa.gov.cn/art/2025/5/26/art_75_199841.html

### 10.2 方案 A：文件生成 + 人工上传（推荐 MVP）

系统生成 OA 答复工作包、纯文本意见、PDF 附件、修改文件、清单和回执归档入口。人工继续在专利业务办理系统完成登录、选择官文、上传、预览、扫码签名和提交。

优点：

- 风险最低。
- 交付最快。
- 与客户当前流程兼容。
- 不绕过人工核对责任。
- 能立即解决重复上传、重复粘贴、格式丢失后的人工整理问题。

缺点：

- 不能做到全自动提交。
- 仍需要人工在官方页面完成最后动作。

建议作为 MVP。

### 10.3 方案 B：半自动辅助填报（P1）

在方案 A 的基础上，系统提供更强的本地辅助：

- 一键复制申请人、意见陈述文本。
- 打开工作包目录。
- 生成操作员逐项勾选清单。
- 生成专利业务办理系统页面字段映射说明。
- 如果客户允许，可提供浏览器侧辅助脚本，但不自动签名、不自动提交。

优点：继续降低重复录入。
缺点：对网页变更敏感，且仍需合规评估。

### 10.4 方案 C：RPA / 网页自动化（不推荐 MVP）

通过浏览器自动化完成登录后页面点击、字段填写、文件上传、回执下载。

主要风险：

- 官方页面、验证码、扫码认证、签名流程变化会导致脚本失效。
- 账号、证书、签名责任边界复杂。
- 用户服务协议对未授权第三方工具接入存在限制。
- 代理业务提交结果具有法律后果，不能把最终提交隐藏在脚本里。

除非客户明确接受风险、完成合规审查，并将最终签名提交保持为人工确认，否则不建议进入 MVP。

### 10.5 方案 D：专利业务办理系统客户端批量接口 / 官方直连（P1/P2）

官方资料显示存在“数据标准规范及批量接口”，可用于与专利业务办理系统客户端进行数据交换。该路径更适合作为可持续增强方向：

- 新申请请求类表格 XML 数据包。
- 部分手续/意见陈述/补正相关 XML 文件包。
- 与 Word 转 XML 输出文件建立关联。
- 由客户端导入后人工核对、签名、提交。

需要进一步确认：

- 客户实际使用的是专利业务办理系统网页版、客户端，还是仍称为 CPC 的旧流程口径。
- 批量接口支持的具体业务表格是否覆盖“答复审查意见”场景。
- 客户 IT 环境是否允许系统生成或写入客户端可导入数据包。
- 批量接口是否只支持离线客户端导入，不提供服务端提交 API。
- 是否有官方授权的第三方接口或合作接入方式。

在没有官方提交 API 证据前，本报告不建议写成“系统直接提交 OA 答复到 CPC”，而应写成“生成符合官方数据标准的可导入包，并在客户端/网页人工核对签名提交”。

### 10.6 外部系统口径复核补充

二次复核后，对 CPC / 专利业务办理系统口径补充如下：

- 客户文档中同时出现“CPC 接口”“专利业务办理系统”“网页”“客户端”等说法，后续需求必须先冻结客户实际终端：网页版、专利业务办理系统客户端，还是旧 CPC 习惯叫法。
- 对新申请递交，客户现有页面路径不是单一上传动作，而是“接收类表格导入 -> 国家申请 -> 发明专利 -> 请求书保存 -> 上传 XML 压缩包 -> 预览/提交 -> 扫码提交 -> 合并 PDF 归档”。工作包必须按这个路径组织文件和提示。
- 对 OA 答复，客户现有页面路径是“云端二次下载官文 -> 意见陈述/补正 -> 答复审查意见 -> 业务办理 -> 填申请人/陈述的意见/附加文件 -> 保存 -> 预览 -> 签名 -> 提交 -> 确认提交 -> 未确认列表批量接收确认 -> 下载电子申请回执”。工作包必须把“下载回执并归档”作为关闭条件，而不是提交后立即关闭。
- 官方“专利电子申请数据标准规范及批量接口”当前应以 2024-01-17 工具下载页为基线；其中批量接口更像客户端数据交换标准，不是已确认的服务端直连接口。
- 若后续要走批量接口，必须拿到客户环境样例并验证：请求类表格 XML、意见陈述/补正场景、文件压缩包、客户端导入、扫码签名、提交回执下载这几段是否都能被数据包覆盖。

## 11. 格式保真方案

客户提到公式、符号、表格、图片复制不过去，这是 OA 答复中最直接的效率痛点。

### 11.1 MVP 策略

使用“双轨输出”：

- Word 正本：代理人工作的原始意见陈述文件，作为内部正本归档。
- 纯文本意见：系统抽取可粘贴到官方“陈述的意见”字段的简洁文本。
- PDF 保真附件：系统把 Word 转成 PDF，保留公式、表格、图片和版式；在“陈述的意见”中引用该附件。

建议意见字段自动生成类似说明：

```text
本次意见陈述详见随附文件《意见陈述书.pdf》。其中涉及公式、表格、附图或特殊符号的内容，以随附 PDF 文件为准。
```

具体文字需由代理人和客户确认，避免不符合官方填写习惯。

### 11.2 后续增强

- Word 到 HTML 的富文本预览。
- Word 数学公式识别为图片或 MathML。
- 表格转图片或 HTML 表格。
- 图片嵌入检查。
- 自动标记“无法安全复制”的段落并提示人工确认。

这些增强不能替代最终核对。官方通知也强调当事人和代理机构需保证 XML 转换和提交文件准确、完整。

## 12. 风险与合规

| 风险 | 说明 | 建议控制 |
| --- | --- | --- |
| 官方提交责任 | OA 答复和新申请提交具有法律后果 | 最终预览、签名、提交保留人工确认 |
| 服务协议风险 | 未授权第三方工具接入可能违规 | MVP 不做网页登录自动提交 |
| XML 转换风险 | 2026 年后 XML 要求更严格 | 生成前校验，生成后人工核对和归档证据 |
| 格式丢失风险 | 公式、表格、图片无法可靠粘贴 | PDF 保真附件优先 |
| 客户流程差异 | CPC、专利业务办理系统网页版/客户端口径可能混用 | 先确认客户实际终端和版本 |
| 字段缺失风险 | 申请人/发明人字段不完整会阻塞提交 | 工作包生成前做缺失项检查 |
| 回执漏归档 | 外部提交完成后内部状态不闭环 | 回执附件作为关闭工作包必填项 |

## 13. 分阶段实施计划

### Phase 0：确认与原型

- 与客户确认 OA 答复真实样本 3-5 个。
- 确认客户使用网页版、客户端、批量接口、Word 转 XML 工具的实际组合。
- 确认可接受的“意见字段说明文字”。
- 确认龙虾邮件系统是否只需交接数据。

交付物：OA 答复工作包原型、字段清单、样例输出目录。

### Phase 1：OA 答复工作包 MVP

- 增加 OA 答复工作包视图。
- 支持 Word/PDF/修改文件/附加文件组织。
- 生成纯文本意见和 PDF 附件。
- 生成提交清单和归档 manifest。
- 支持回执上传和内部任务关闭。

验收：同一 OA 答复场景下，操作员不再需要从多个内部页面手工找申请号、申请人、官文、意见陈述、修改文件和回执归档入口。

### Phase 2：新申请递交包与字段补齐

- 增加申请人/发明人递交字段补录检查。
- 输出新申请递交工作包。
- 关联 Word 转 XML 输出压缩包。
- 生成请求类表格字段清单。

验收：新申请递交前能一次性看到缺失字段和待上传文件。

### Phase 3：客户端批量接口增强

- 研究官方 2024 数据标准与批量接口文件。
- 针对客户高频表格生成可导入数据包。
- 先从新申请或固定补正表格切入，再扩展 OA 答复。

验收：客户可在专利业务办理系统客户端导入系统生成的数据包，并人工核对提交。

### Phase 4：信函生成与邮件交接

- 建立官文到格式函模板映射。
- 实现命名规则和联系人抬头。
- 输出给龙虾系统的邮件标题、正文、附件路径或交接清单。

验收：官方通知入库后，能自动生成对应客户信函 Word 和邮件交接数据。
