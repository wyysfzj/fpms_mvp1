# FPMS 客户演示方案

## 1. 演示目标

- 本次演示要向客户证明：FPMS 当前版本已经能够围绕事务所最核心的“客户建档、案件建档、来文处理、期限协同、费用草稿、账单、回款、核销”形成一条可运行的业务链路，而不是零散功能拼接。
- 当前版本最值得展示的业务价值，是把专利代理事务所日常最常见、最容易出风险、也最容易影响回款效率的几件事串起来：案件信息集中、OA 处理有抓手、费用生成有依据、财务闭环可追踪。
- 对合伙人和管理层，应重点证明三件事：第一，业务过程是否透明；第二，时限和收费是否能落到系统里；第三，管理层能否快速看到案件推进和回款状态。
- 本次 Demo 以当前可运行版本为边界，主演示聚焦 `Clients / Cases / Documents / Tasks / Fees / Billing / Dashboard / System` 已有能力；尚未完全落地的蓝图能力不放入主演示流程。

## 2. 演示对象与关注点

| 演示对象 | 最关心的问题 | 当前系统回应方式 | 演示时要突出什么 |
|---|---|---|---|
| 合伙人 | 案件有没有漏管、费用有没有漏收、团队忙不忙得过来 | 用工作台、案件详情、任务记录、账务摘要展示当前状态 | 经营视角、风险视角 |
| 管理层 | 从客户到案件到收费，流程是否可追踪 | 用案件详情中的公文、任务、费用、账务页签串起来讲 | 流程视角、协同视角 |
| 业务负责人 | OA、授权通知、收费动作是否能形成闭环 | 用文书触发任务、文书触发费用草稿两条链路展示 | 标准化执行、可复制性 |
| 财务负责人 | 费用草稿、账单、回款、核销是否能打通 | 用费用草稿、账单详情、回款登记、案件账务摘要展示 | 财务闭环、催收基础 |
| 流程主管 | 日常操作是否顺手，是否便于交接 | 用客户、案件、公文、任务页面演示操作路径 | 落地性、可执行性 |

- 演示时不要把重点放在“系统字段很多”上，而要放在“事务所关键动作终于能留痕、能协同、能追账”上。
- 经营视角建议重点讲“案件推进透明度”“回款闭环”“工作台抓手”。
- 流程视角建议重点讲“收文后自动形成任务”“授权通知后自动进入收费动作”。
- 风险控制视角建议重点讲“期限有提醒、费用有草稿、账单和回款能对应到案件”。

## 3. Demo 总体故事线

本次 Demo 建议采用“两条主线、一条总览”的讲法。第一条主线是“客户建档与案件建档”，用于证明系统不是从中间环节切入，而是从事务所最基础的客户与案件主档开始沉淀；第二条主线分成两段，一段展示“OA 收文 → 自动生成任务 → 答复后任务闭环”，另一段展示“授权通知 → 自动费用草稿 → 账单 → 回款/核销 → 案件账务摘要”。最后回到工作台和系统配置，说明管理层如何看结果、系统如何支持配置化运行。

这条故事线适合当前版本，有三个原因。第一，它完全落在当前已有页面和已验证接口之内，不依赖未上线能力。第二，它能覆盖事务所最熟悉的中国专利代理场景，既有流程侧的 OA，也有财务侧的授权收费。第三，它能够做到“先建档、再推进、再收费、再闭环”，客户一听就知道这套系统是为日常经营准备的，而不是只做单点工具。

建议现场采用“少量现场创建 + 关键数据预置”的方式。现场只演示新建客户和新建案件，证明基础建档能力；OA 场景和授权收费场景使用同一客户下预置好的真实样例数据继续往下讲，这样既真实，又能保证现场节奏稳定。

## 5. 演示场景分幕设计

### 第一幕：从客户到案件，先证明基础主档能力

- 场景名称：客户与案件建立
- 演示目标：先让客户相信系统能把事务所最基础、最常用的客户与案件主档收进去，并形成后续所有流程的起点。
- 操作入口：`客户管理 Clients`、`案件管理 Cases`
- 关键演示动作：新建“苏州智元精密制造有限公司”；进入案件管理，新建 `ZY-IP-2026-D-003` 外观设计案件；保存后进入案件详情。
- 页面上应该看到的关键结果：客户列表出现新客户；案件列表出现新案件；案件详情页可看到概览、公文、任务、费用、账务等页签已具备后续承载能力。
- 讲解词：这一步不是简单建个档，而是把客户、案件、后续公文、期限、费用、回款都挂到同一条主线上。对事务所来说，基础主档一旦标准化，后面每个岗位看到的就是同一件事，而不是各自一套表。
- 本幕要传达的业务价值：客户和案件不再分散在 Excel、邮件和个人习惯里，事务所后续每一个动作都有明确归属对象。

### 第二幕：用 OA 收文场景展示流程协同与期限控制

- 场景名称：文书驱动任务生成
- 演示目标：证明系统不只是存文书，而是能把“收文”转成“要做的事”。
- 操作入口：建议从 `案件管理 Cases` 打开 `ZY-IP-2026-I-001` 详情，再进入公文记录；也可直接进入 `Documents`
- 关键演示动作：展示该案的 `OA_IN` 收文记录；如需要增强真实感，可打开文书详情并展示附件；切换到任务页签或任务列表，查看系统自动生成的“OA 答复期限”任务。
- 页面上应该看到的关键结果：该收文标识为需要回复；任务列表中出现与案件关联的打开任务；案件右侧或任务列表能看到截止日期和内部提前提醒。
- 讲解词：专利代理业务里，真正高风险的不是文书存没存下来，而是收文以后有没有被及时变成待办。当前版本已经能把典型 OA 收文转成任务，并给出绝限和内部处理节奏，这样流程主管和代理人看到的是同一条任务，而不是靠转邮件和口头提醒。
- 本幕要传达的业务价值：把“知道来了文”升级成“明确谁来做、什么时候做、有没有做完”。

### 第三幕：用答复动作展示期限闭环

- 场景名称：答复后自动闭环
- 演示目标：证明任务不是孤立存在，答复动作能回到案件链路里。
- 操作入口：`Documents` 或 `案件详情 > 公文记录`，再切到 `Tasks`
- 关键演示动作：展示 `OA_OUT` 答复文书，并说明其回复来源是前面的 OA 收文；返回任务列表或任务详情，展示对应任务已由打开转为完成；如果需要，可展示任务日志时间线。
- 页面上应该看到的关键结果：原收文出现“已回复”；任务状态变为已完成；案件详情中公文和任务信息前后一致。
- 讲解词：这一步是事务所非常在意的地方。很多系统能记收文，也能记任务，但做完答复以后，文书和任务仍然是两张皮。当前版本的亮点，是把答复文书和前面的待办串起来，让流程闭环能被看到、能被追溯。
- 本幕要传达的业务价值：文书处理、代理动作、流程状态不再脱节，减少漏答、迟答、重复催办的风险。

### 第四幕：用授权通知展示收费动作如何自然落地

- 场景名称：授权通知触发费用草稿与账单
- 演示目标：证明收费不是脱离案件单独做，而是可以承接业务事件。
- 操作入口：`案件管理 Cases` 打开 `ZY-IP-2026-I-002`，再进入 `费用草稿 Fees` 与 `账单 Billing`
- 关键演示动作：先展示 `GRANT_NOTICE` 授权通知文书；切到费用草稿列表或案件费用页签，查看系统已形成的授权费用草稿；补充或确认费用项后锁定草稿；从草稿生成账单，打开账单详情。
- 页面上应该看到的关键结果：费用草稿已关联到案件与客户；费用项与金额清晰可见；账单号生成后，账单详情中可以看到金额、余额、客户、案件关联关系；若现场已配好模板路径，可点击打印账单。
- 讲解词：授权通知之后要不要收费、收什么、由谁开单，是很多事务所容易靠经验和聊天解决的环节。当前版本已经能把授权通知往收费动作上接，先形成费用草稿，再形成账单，这样收费依据和案件事件是一致的。
- 本幕要传达的业务价值：收费动作前移并且有依据，减少“该收没收”“收了但说不清为什么”的情况。

### 第五幕：用回款与核销展示财务闭环

- 场景名称：回款、核销与案件账务闭环
- 演示目标：证明系统不仅能开单，还能把回款与案件连接起来。
- 操作入口：`回款与核销 Payments`、`账单详情 Bill Detail`、`案件详情 > 账务`
- 关键演示动作：登记一笔 1,700 元银行回款；在回款页面创建核销，把该回款对应到 `FPMS-BILL-202603-0088`；打开账单详情，查看余额归零；回到案件详情账务页签，查看累计开票、累计回款、未结清金额。
- 页面上应该看到的关键结果：回款已登记；账单余额归零；案件账务摘要显示该案已形成可追踪的收费闭环；如要加演，可演示一次冲销，把账单恢复为未结清。
- 讲解词：对管理层来说，最关心的不是系统能不能记一笔回款，而是这笔钱最后落到了哪一个客户、哪一个案件、哪一张账单。当前版本已经能把账单、回款、核销和案件账务摘要连起来，事务所至少具备了做经营穿透的基础。
- 本幕要传达的业务价值：从“记账”走向“按案件看钱、按客户看钱、按状态看钱”。

### 第六幕：回到管理视角，展示工作台与配置化基础

- 场景名称：管理总览与配置化亮点
- 演示目标：让合伙人看到结果，让业务负责人看到系统不是靠硬编码运转。
- 操作入口：`Dashboard`、`System / 文件模板`、`System / 任务模板`、`System / 系统参数`
- 关键演示动作：先看工作台中的待处理任务、未开票草稿、案件流程阶段；再进入文件模板和任务模板，点出 `OA_IN → OA_REPLY`、`GRANT_NOTICE → GRANT_FEE` 这两条配置关系；最后简单展示账单模板路径参数。
- 页面上应该看到的关键结果：工作台能快速看到案件和待办的聚合视图；模板页面能看见文书模板、任务模板和启用状态；系统参数可维护模板路径。
- 讲解词：这一步不是为了展示系统设置多复杂，而是想说明一件事：这套系统不是只能做一两条演示链路，而是已经具备“通过模板和参数去支撑事务所标准作业”的基础能力。对事务所而言，这意味着后续扩展更可控。
- 本幕要传达的业务价值：管理层有抓手，业务负责人有标准化基础，系统具备继续扩展的空间。

| 8 | 第二条主线看收费闭环。这里是一件授权通知样例案。授权通知进来以后，系统已经把收费动作往前带了一步，先形成费用草稿。 | `Cases > ZY-IP-2026-I-002`，再到 `Fees` | 案件事件能自然带出收费动作 |
| 9 | 费用草稿里我们可以确认官方费和服务费，确认后锁定，再一键生成账单。这样账单不是凭空来的，而是有案件依据、有费用依据。 | `Fee Draft Detail`，再到 `Bill Create` 和 `Bill Detail` | 草稿、账单、案件、客户四者关系清晰 |
| 10 | 如果现场环境已经配好模板，我会直接点打印账单。对客户来说，这说明系统已经具备从业务数据到正式输出物的能力。 | `Bill Detail > 打印账单` | 系统不仅记录，还能产出对外交付物 |
| 11 | 财务闭环再走一步。这里登记一笔客户回款，然后做核销。核销之后，账单余额归零，回到案件详情还能看到累计开票、累计回款和未结清。 | `Payments`，再回 `Bill Detail` 与 `Cases > 账务` | 钱已经能落到具体案件，不再只是账上记一笔 |
| 12 | 最后我回到系统设置简单看一眼。这里能看到文书模板、任务模板和参数配置，所以前面的动作不是写死在程序里，而是在逐步沉淀成事务所自己的规则。 | `System / 文件模板`、`任务模板`、`系统参数` | 当前版本已经具备标准化和继续扩展的基础 |

### 现场停顿与强调建议

- 在 OA 收文生成任务时停顿 2 秒，强调“这一步解决的是漏期限、漏催办”。
- 在费用草稿生成账单时停顿 2 秒，强调“收费依据来自案件事件，不是财务单独再做一遍”。
- 在账单余额归零、案件账务摘要更新时停顿 2 秒，强调“这才是管理层能真正拿来看的经营抓手”。

## 7. 演示中的风险点与规避方式

- 风险点：把工作台当成完整 BI 报表来讲。
  规避方式：明确把 `Dashboard` 定位为“管理总览入口”和“业务穿透入口”，不要承诺它已经是完整经营分析平台。

- 风险点：在回款页重点展示“核销记录列表”。
  规避方式：当前版本核销更适合演示“创建核销”和“在账单详情看到余额变化”；不要把“完整核销台账”当成主营亮点。

- 风险点：现场点击“打印账单”但模板路径未配置。
  规避方式：演示前先在 `System / 系统参数` 确认 `bill_template_path`；如未准备好，就把打印动作改成口头说明，不要现场冒险。

- 风险点：OA 自动任务或授权自动费用草稿没有触发。
  规避方式：演示前先在 `System / 文件模板` 确认 `OA_IN`、`OA_OUT`、`GRANT_NOTICE` 已启用；在 `System / 任务模板` 确认 `OA_REPLY`、`GRANT_FEE` 已启用。

- 风险点：页面中部分创建动作需要手工输入案件 ID、客户 ID。
  规避方式：提前准备一张“小抄”，列出本次演示的客户编号、案件编号、草稿编号、账单号，避免现场来回查找。

- 风险点：附件上传或下载受浏览器环境影响。
  规避方式：提前准备 2 到 3 个小体积 PDF 文件，并在演示浏览器里允许下载；如果现场网络或浏览器策略不稳定，可只展示附件已存在的详情页。

- 风险点：频繁切换不同权限账号影响节奏。
  规避方式：现场统一用管理账号操作，讲解时用“流程主管视角”“代理人视角”“财务视角”来带入，不建议为了权限演示反复登录退出。

- 风险点：把路线图功能讲成当前已上线。
  规避方式：凡是 PCT、复杂年费、完整催款坏账、提成结算、重报表分析等内容，都统一放到最后“后续演进方向”里说。

## 8. 本次 Demo 能证明的价值总结

- 当前版本已经能把事务所最核心的案管主线跑起来：客户、案件、公文、任务、费用、账单、回款不是分散页面，而是可以围绕同一案件连续追踪。
- 对流程管理来说，OA 收文后自动形成任务、答复后形成闭环，已经可以显著提升案件处理透明度。
- 对财务管理来说，费用草稿、账单、回款、核销已经能围绕案件沉淀，为后续催收、分析和经营复盘打基础。
- 对管理层来说，系统已经具备“从总览看问题、从案件穿透到明细”的基本能力，适合作为事务所进一步数字化运营的底座版本。
- 对客户来说，这不是概念验证式产品，而是已经贴近中国专利代理事务所日常业务动作的可运行版本。
