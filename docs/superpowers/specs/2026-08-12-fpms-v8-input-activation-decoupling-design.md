# FPMS V8 用户输入与生产激活解耦设计

日期：2026-08-12

状态：已获客户原则批准，待独立规格复审和书面采用
风险：HIGH（收费、客户配置、来源激活、证据谱系）

## 1. 决策摘要

官方缴费工作簿和客户服务价格表都是机构在系统上线或运营期间提供、更新和审批的
**用户输入**，不是开发团队完成相应功能的前置材料。因此，V8 将原来单一的“已就绪”
拆成两个互不混淆的状态：

1. `CAPABILITY_READY`：载体、上传、校验、版本、审批、API、既有任务约定的 UI、审计、
   失败关闭行为和测试已实现并独立验收；
2. `PRODUCTION_INPUT_ACTIVE`：机构提供的真实输入已经受控上传、校验、审批并在明确的
   生效范围内激活。

缺少真实输入只能使第二个状态保持未激活，不能阻止第一个状态的开发和验收。系统在
第二个状态未满足时必须明确返回 `409` 且不写入业务状态，不能使用样例数据、默认价格、
历史文件或推断值替代真实输入。

## 2. 权威与不变边界

本设计实施客户在当前会话中确认的边界：

- 11 行缴费工作簿任务所需的清洁当前工作簿及受控上传证明由用户提供；
- 8 行服务价格任务所需的完整获批价格版本由用户提供；
- 两类输入的暂时缺失不影响能力实现，但影响真实生产激活。

以下规则保持不变：

- `DG-PAYMENT-WORKBOOK:GLOBAL` 和 `DG-SERVICE-RATE-VERSION:GLOBAL` 继续作为精确的生产
  激活身份，不能伪造为已确认；
- 官方费与服务费是两个独立事实域，服务价格不得改变、覆盖或推导官方费；
- 未配置、未审核、失效、版本或哈希不匹配、范围不符、来源不明时均失败关闭；
- 生成工作簿不等于官方接收、缴费或票据核验；四个事实继续分开记录；
- 付款工作簿的宏只保留，永不在服务端执行；
- 原始输入、上传证明、校验结果、版本、哈希、审批人、操作人、时间和原因均须可审计；
- 本设计不修改已经冻结的 catalog 字节，而通过精确 successor contract 修正其旧依赖解释。

## 3. 状态模型

| 能力 | 能力实现状态 | 生产输入状态 | 允许行为 |
| --- | --- | --- | --- |
| 尚未实现 | `NOT_READY` | 任意 | 不可用 |
| 已实现、无真实输入 | `CAPABILITY_READY` | `CONFIG_REQUIRED` | 可运行隔离测试；生产动作 409/无写入 |
| 已上传、未审核或校验失败 | `CAPABILITY_READY` | `PENDING_REVIEW` / `INVALID` | 管理操作和审计可见；生产动作 409/无写入 |
| 已审核且处于有效范围 | `CAPABILITY_READY` | `PRODUCTION_INPUT_ACTIVE` | 在权限、范围和其他业务条件同时满足时允许生产动作 |
| 输入过期、撤销或被新版本替代 | `CAPABILITY_READY` | `INACTIVE` | 新生产动作 409/无写入；历史版本和谱系保留 |

`CAPABILITY_READY` 只描述代码和工程验收，绝不能作为价格、法律状态、缴费义务或官方接收
的业务事实。

## 4. 官方缴费工作簿能力

### 4.1 现在必须实现

依据既有 rows 214–222 和 278 的闭包，开发并验收：

- `.xlsm` 输入载体、受控上传、原始文件与上传证明保存；
- 工作表、列、数据验证、隐藏内容和 VBA 结构的只读检查与保留；
- 模板版本、内容哈希、来源、适用范围、生效区间和审批状态；
- 经激活真实模板的填充、正式生成、下载、API、前端适配和 UI；
- 同一 PayList 下对官方站点接收证据的独立记录、API、前端适配和 UI；
- 生成、官方接收、实际缴费、票据核验四个独立事实的 E2E 验证；
- 缺失、过期、撤销、哈希/结构/范围不符时的 `409 / NO WRITE`；
- 宏保留但服务端从不执行。

本设计不额外发明 catalog 未要求的第二套页面或接口。受控上传/审批所需的精确载体和
管理入口由后续实施计划复用现有配置/证据模块，或在发现真实缺口时物化最小 successor
任务。

### 4.2 测试输入与真实输入

row 214 的测试 fixture 是合同完整的合成 `.xlsm`，只证明处理引擎能够保留和校验已冻结的
结构不变量；它不代表客户真实模板，也不证明与客户未来上传版本兼容。真实文件在每次
激活前仍须执行同一套结构、哈希、范围和审批检查。

测试 fixture 必须带有不可混淆的 `TEST_ONLY` 来源分类，并且同时满足：

- 只存在于测试资产或隔离测试存储；
- 生产环境拒绝其注册、激活和正式生成；
- 不能作为 seed、默认模板、故障回退或首次启动配置；
- 不能仅凭文件名判断测试属性；必须由受信环境和持久化来源分类共同约束。

### 4.3 生产激活边界

只有机构提供清洁的当前真实 `.xlsm`，并提交受控上传证明，且文件结构、版本、哈希、范围
和审批均有效后，`DG-PAYMENT-WORKBOOK:GLOBAL` 才能进入生产激活状态。在此之前：

- 管理员可以上传、查看校验结果和发起审批；
- 正式工作簿生成与后续真实接收证据链不得使用测试模板；
- 生产生成请求返回 409，并且不得创建 artifact、FEE activity 或改变 PayList 状态。

## 5. 服务价格能力

### 5.1 现在必须实现

依据既有 rows 223–229 的闭包，开发并验收：

- 版本化服务价格载体，以及不可变 item snapshot、来源哈希、币种、税、折扣和范围字段；
- 来源支持的完整价格版本导入、字段和十进制金额校验、唯一 item code、内容哈希和幂等；
- 导入 API 创建或复用 `DRAFT`，导入本身不激活；
- 对已填充、已审批、无重叠且来源有效的版本进行激活，以及相应 API；
- 使用精确 active `price_book_version_id + item_code + case_id` 创建服务费应收及 API；
- 缺失、空、格式错误、未审批、过期、重叠、哈希/范围不符时的 `409 / NO WRITE`；
- 服务费与官方费分域，不能由官方费自动推导服务应收。

既有 catalog 未冻结独立的服务价格管理 UI，因此本 successor 不擅自增加 UI；如后续核对
现有系统确实没有任何可用的管理员输入入口，应把该单一缺口物化为新的最小任务，而不是
扩大 rows 223–229 的闭包。

### 5.2 测试输入与真实输入

测试使用完整但虚构的 `TEST_ONLY` 价格版本，覆盖导入、审批、激活和应收 happy path。
其隔离规则与工作簿一致：生产环境拒绝注册/激活，不能作为 seed、默认价或回退价，也不能
因名称看似“测试”就获得特殊信任。

真实生产输入必须由机构上传完整价格版本，保留原始来源和内容哈希，并经过授权审批。
只有精确版本在适用范围和生效区间内处于 active，才允许报价或创建服务费应收。未满足时
生产请求返回 409 且不创建 obligation、line、activity 或其他应收状态。

## 6. Catalog successor 映射

本设计不改动 `docs/product/v8/catalog.frozen.json`；后续物化一个精确的 successor authority，
只替换下列 rows 的“必须先有真实输入才能开始开发”解释：

| Rows | 任务族 | 新的开发资格 | 保留的生产门禁 |
| --- | --- | --- | --- |
| 175 | 缴费工作簿 lane manifest | 可在真实输入缺失时物化开发/验收 lane | 不得宣布生产模板已激活 |
| 176 | 服务价格 lane manifest | 可在真实输入缺失时物化开发/验收 lane | 不得宣布生产价格版本已激活 |
| 214–218 | 工作簿适配、生成、HTTP、FE、UI | 使用 `TEST_ONLY` fixture 实现和验收 | 正式生成仍要求有效真实模板 |
| 219–222 | 官方接收证据 service/API/FE/UI | 使用隔离场景实现和验收 | 不得把测试接收证据写入生产 |
| 223–225 | 服务价格 carrier/import/API | 可实现；真实输入可导入为 DRAFT | 不能因导入而激活或计费 |
| 226–227 | 服务价格 activation/service API | 使用隔离 fixture 验证状态机 | 生产激活须真实完整获批版本 |
| 228–229 | 服务应收 service/API | 使用隔离 fixture 验证精确来源链 | 生产应收须精确 active 真实版本 |
| 278 | 工作簿真实路径 UI E2E | 用隔离 E2E 证明四事实分离及未配置态 | 不宣称真实 CNIPA 接收或付款 |

这里的“开发资格”不删除各任务原有 closure、non-closure、allowlist、权限、TDD、独立 review、
scope 和 evidence 要求。只解除错误的前置关系，不改变运行时 fail-closed 条件。

## 7. Full、Final 与 Release 的新解释

Full/Final 验收关注软件是否完整、安全地支持这两类用户输入，而不是要求测试期间持有客户
的生产数据：

- 允许以 `CAPABILITY_READY + CONFIG_REQUIRED` 关闭开发；
- 必须证明两条生产 lane 在缺少真实输入时明确禁用，返回 409 且零业务写入；
- 必须证明 TEST_ONLY 输入不能跨入生产配置；
- 必须覆盖权限、版本/哈希、范围/区间、审批、撤销/替代、谱系和审计；
- row 281 的回归矩阵、row 282 的逐项 ledger 和 row 283 的最终 close 可以在上述负向状态
  完整受验后执行；
- release receipt 必须明确记录 `payment_workbook=CONFIG_REQUIRED` 与
  `service_rate=CONFIG_REQUIRED`（若届时仍无真实输入），不得声称两项功能已生产激活；
- 后续机构提供输入并激活属于受控配置发布，不需重新开发，但仍需输入级验证、独立审批和
  审计。

这种关闭方式只解决“代码是否完成”，不把缺少用户配置描述为业务完成，也不生成任何虚假
收费或支付事实。

## 8. API、事务和审计要求

- 受保护管理和业务端点继续使用既有 `Fee.Edit` 等精确权限；认证 401、授权 403；
- 缺少或冲突配置使用 409，显式载荷校验使用 400/422，保持现有响应 envelope；
- 服务层不自行 commit；调用方拥有事务。任何失败都 rollback 且无半成品业务状态；
- 上传、校验、审批、激活、撤销/替代、生成和应收创建记录真实 actor、server time、版本、
  内容哈希、原因和前后状态；
- 原始文件/价格源不可被派生物覆盖，历史版本不能因新版本激活而丢失；
- 重放只在所有身份、版本、哈希和结果一致时幂等，否则 409。

## 9. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| TEST_ONLY 工作簿的隔离测试生成 | 测试环境成功，结构/VBA 保留，宏未执行 |
| 生产无真实工作簿 | 409；无 artifact、activity、PayList 状态变化 |
| 工作簿未审批、过期、撤销、哈希/结构/范围冲突 | 409；无写入；审计保留已有配置事实 |
| TEST_ONLY 工作簿进入生产激活 | 拒绝；无 active 配置 |
| TEST_ONLY 价格版本的隔离 happy path | 测试环境可覆盖导入、激活和应收精确来源链 |
| 生产无获批完整价格版本 | 激活、报价/应收 409；无 obligation/line/activity |
| 空、畸形、重叠、未审批、过期或范围不符价格版本 | 409；无写入 |
| TEST_ONLY 价格版本进入生产激活 | 拒绝；无 active 价格版本 |
| 服务价格变化 | 不改变任何官方费率、官方费义务或缴费事实 |
| Full/Final 时两项真实输入仍缺失 | 能力可 PASS；release 明示 CONFIG_REQUIRED，不声称已激活 |

## 10. 实施顺序

1. 物化一个 successor authority/adoption 任务，精确绑定本设计并修正 rows 175、176、
   214–229、278 与 Full/Final 的依赖解释；不改 frozen catalog。
2. 更新两条 lane manifest，使能力任务在 `CONFIG_REQUIRED` 下可执行，同时保留生产 gate。
3. 先做 carrier/import/validation，再做 activation，最后做正式输出/应收与 UI/E2E；共享 schema、
   router、SQLite 写测试串行。
4. 每项使用既有原子任务 closure、targeted TDD、独立 HIGH review 和 fast close；不得重做已
   完成证据。
5. 两条 lane 终态 PASS 后执行 row 281、282、283；release 永远最后，并记录真实配置状态。

## 11. 非目标

- 不提供或猜测客户真实工作簿、服务价格、折扣、税率或收费决定；
- 不以测试 fixture、旧模板或网站示例作为生产来源；
- 不执行 VBA，不自动申报、不推断 CNIPA 接收、缴费或票据核验；
- 不合并官方费与服务费；
- 不借本设计重构邻接模块、扩展权限或新增未经 catalog/后续精确任务冻结的 UI。

## 12. 完成标准

本设计被独立 HIGH reviewer 以零 P0/P1/P2 finding 通过并由用户书面采用后，才进入实施计划。
实施完成的最终判据是：两条能力链均独立验收，真实输入缺失路径 fail-closed，TEST_ONLY 隔离
被证明，Full/Final/Release 明示实际配置状态，且没有虚构生产激活、收费、支付或来源事实。
