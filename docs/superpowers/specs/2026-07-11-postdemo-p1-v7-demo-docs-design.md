# FPMS P1 V7 Demo Documents Design

## Objective

Create three standalone V7 documents for the next customer demo while retaining V6 as immutable
historical execution evidence. V7 must translate the completed seven-GAP mitigation into accurate
business-facing design, presenter steps, and an executable readiness runbook.

## Story Shape Classification

- `shared_file_density`: low
- `prereq_dependency_density`: medium
- `be_fe_coupling`: low
- `evidence_cost`: medium
- `chosen_runbook`: `P0-multi-lane-parallel-story`

## V7 document set

1. `docs/postdemo/postdemo_p1_lifecycle_demo_design_v7_20260711.md`
   - Authoritative V7 business/demo model.
   - Defines the one-case lifecycle, four state dimensions, real-path versus enrichment boundary,
     seven mitigated GAP capabilities, fail-closed behavior, and success criteria.
2. `docs/postdemo/postdemo_p1_lifecycle_demo_script_v7_20260711.md`
   - Presenter-facing, step-by-step script.
   - Each step states purpose, inputs, buttons, observable result, four-state transition, presenter
     language, failure demonstration, and recovery.
3. `docs/postdemo/postdemo_p1_v7_ui_e2e_success_runbook_20260711.md`
   - Operator-facing readiness and execution runbook.
   - Defines cleanup, environment, permissions, mixed real-path data preparation, checkpoints,
     stop conditions, evidence, recovery, and post-demo cleanup.

This planning spec—not the output of Task 1—is the complete frozen contract shared by all three
parallel authoring tasks. Task 1 explains the contract to business readers but is not a prerequisite
file consumed by Tasks 2 or 3.

## Canonical business contract

- Customer and case are created through the UI.
- Filing and OA work packages use deterministic existing-first resolve paths and must not depend on
  enrichment.
- The document wizard uses the bounded real template list; the catalog displays all 60 official
  notices with Chinese `可执行` / `仅供参考` classification. Reference-only rows are not actionable.
- Every executable OA or grant notice carries a complete explicit official-deadline tuple: date,
  source, and `CONFIRMED` status. Missing, malformed, or conflicting input fails closed.
- OA_OUT creation does not close the OA task or restore the case. A same-case receipt with the
  correct OA source, complete metadata, and successful archive transaction closes exactly one task
  and restores the case. A later OA creates a distinct source/package/task identity.
- A grant notice creates a source-linked confirmed grant task but no premature fee draft. Client
  instruction is required before the normal draft path.
- Grant replacement creates a new confirmed task and marks the old task superseded. Direct draft,
  batch instruction, notice generation, and state mutations fail closed for the superseded task;
  UI actions are disabled or hidden accordingly.
- Document create and its required side effects are atomic.

## Mixed real-path strategy

The core GAP path—wizard/catalog, filing/OA resolve, structured deadline, receipt ownership/archive,
grant lineage/replacement/mutation—is demonstrated using real public UI/API behavior without route
mocking, direct database writes, or enrichment.

Minimal post-creation enrichment remains allowed only for application-fee, format-letter, and
annuity fixtures that the current UI cannot construct end-to-end during a practical demo. Each use
must identify the exact records created, state that it is demo support rather than production
behavior, and must not overwrite UI-created customer/case facts or any core GAP object.

## Customer-language boundary

- Use Simplified Chinese business language and visible labels.
- Do not present internal enum values, IDs, status/error codes, or test implementation as the main
  customer narrative.
- Do not promise direct official-system submission, RPA, automatic signature, automatic receipt
  download, automatic payment, or automatic email sending.
- Technical error codes may appear only in an operator-only troubleshooting appendix.

## Consistency rules

- Design defines meaning; script instantiates it; runbook verifies it.
- All three documents use the same V7 case/customer naming and the same four state dimensions.
- Every script step maps to a runbook checkpoint.
- The design and script distinguish work-package readiness from official submission/legal-state
  evidence; opening or resolving a preparation package alone does not prove official submission.
- V6 files remain unchanged.

## Acceptance

- Three new V7 files exist and are independently understandable.
- Every target contains all seven canonical IDs in its mandatory matrix; no `where relevant`
  exception is permitted.
- No core GAP step relies on enrichment, route mocking, database injection, or manual status
  storytelling.
- Every residual limitation is explicit and no out-of-scope automation is promised.
