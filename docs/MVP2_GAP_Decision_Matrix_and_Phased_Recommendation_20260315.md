# MVP2 GAP 决策矩阵与分阶段建议（基于 `docs/gap.md`）

## 1. 文档目的

本文件不是重复记录 GAP，而是将 [`docs/gap.md`](/Users/cfcc/Workshop/myprojects/fpms_mvp1_blueprint_atomic/docs/gap.md) 中逐章识别的问题，转化为可执行的 MVP2 决策清单，用于第二轮 discussion 后的立项、排期、任务拆分与验收。

适用范围：

- 来源 2：[`docs/FPMS SPEC 2.0.md`](/Users/cfcc/Workshop/myprojects/fpms_mvp1_blueprint_atomic/docs/FPMS%20SPEC%202.0.md)

本文件的核心目标是回答 4 个问题：

1. 哪些 GAP 必须进入 MVP2？
2. 哪些 GAP 应以“新模型替代旧心智”而不是直接复刻？
3. 哪些 GAP 属于平台/运维范围，应从业务 backlog 中剥离？
4. MVP2 应按什么顺序推进，才能兼顾业务价值、迁移风险和实施成本？

## 2. 决策原则

### 2.1 决策标签

- `A 保留重建`：旧系统能力仍有高业务价值，且不重建会明显影响上线。
- `B 新模型替代 + 迁移说明`：不复刻旧对象，但要补过渡视图、映射规则或操作说明。
- `C 下沉为平台/实施能力`：不是核心业务模块功能，单独纳入平台治理或实施交付。
- `D 延后到 Post-MVP2`：有价值，但不是 MVP2 上线门槛。
- `E 明确放弃`：旧能力不再建议保留，只保留替代方案。

### 2.2 判断标准

- `业务闭环性`：是否影响案件、文书、时限、费用、账单、提成主链路。
- `高频作业性`：是否属于流程人员、财务人员、代理人助理的日常高频操作。
- `迁移阻力`：如果不承接，是否会导致老用户无法迁移。
- `架构一致性`：是否会破坏现有 Web 化、模块化、模板化架构方向。
- `实施替代性`：是否可以通过培训、配置、实施规则而非产品功能解决。

## 3. 总体判断

### 3.1 第二轮讨论后建议形成三条并行轨道

- `Track A 业务迁移补强`
  - 目标：补足 TXX 中仍有高业务价值、且当前 `SPEC` 未完全承接的能力。
  - 重点：工作台、历史补录、固定报表、查询结果工作集、财务操作台、提成迁移视图。

- `Track B 新旧心智映射`
  - 目标：不回退到桌面时代对象模型，但必须给老用户明确迁移路径。
  - 重点：`TemplateCode` 迁移、旧时限类别迁移、旧“代理人结账单”到 `Commission` 模型映射、旧报表口径映射。

- `Track C 平台与运维治理`
  - 目标：承接旧系统中被归在“系统设置”的非业务能力。
  - 重点：运行参数、文件路径、人员主数据、密码/会话、备份/清理、更新机制、词库。

### 3.2 MVP2 总体优先级

- `P0 先做`：影响主业务迁移与上线可用性的内容。
- `P1 次做`：高频效率与旧用户心智补偿。
- `P2 后做`：平台治理与高级模板等非上线阻断项。

建议 MVP2 不追求“完整复刻 TXX”，而追求：

- 主链路可用
- 高频岗位顺手
- 新旧口径可解释
- 历史迁移可落地

## 5. MVP2 分阶段建议

### 5.1 Phase A: 迁移阻断项清零

目标：先解决“业务已能做，但老用户迁不动”的问题。

建议纳入：

- 案件工作台
- 中间文件工作台
- 时限监控台
- 账单工作台
- 收款查询台账
- 历史已缴官费补录
- 查询结果工作集与跨模块导航
- 旧名称规则到 `TemplateCode` 迁移
- 旧时限类别到新 `TaskTemplate` 迁移
- 旧“代理人结账单”到新提成模型的术语与视图映射
- “费用草单代理费小计”到新财务口径的映射说明

交付结果：

- 老用户能按熟悉的工作路径完成主链路操作。
- 实施团队有明确的数据迁移和培训素材。

### 5.2 Phase B: 高频效率与经营视图补强

目标：让流程人员、财务人员、管理层在 Web 系统里达到可接受效率。

建议纳入：

- 年费/年登印费检索结果保存与恢复
- 草单层欠款筛选
- 草单/账单到相关模块的跨模块联动
- 模板中心
- 模板组别与创建/修改向导
- 数据域/计算域目录
- 快捷模块机制
- 固定统计范围面板
- 常用固定经营报表
- 收款账户/汇款地址配置
- 催款单维护与历史查询
- 提成工作台与人工调整能力

交付结果：

- 高频岗位不再依赖大量人工记忆和页面跳转。
- 管理层获得接近旧系统的固定经营报表。

### 5.3 Phase C: 平台治理与高级输出

目标：补足系统级治理能力与复杂输出能力，但不阻断 MVP2 上线。

建议纳入：

- 运行参数/文件路径参数
- 认证、密码、会话重登
- 备份/清理/更新 runbook
- 中外文对照词库
- 固定格式通知函
- 固定格式账单/报表/草单打印
- 时限单打印
- 国专远程缴费客户端集成
- 连续表格等高级 Word 模板能力
- 查询结果套打 Word 表格模板
- 定额完成量法

交付结果：

- 平台治理闭环更完整。
- 特定客户的历史兼容需求得到满足。

## 6. 建议的 MVP2 Epic 切分

建议在 Jira 或任务系统中按以下 10 个 Epic 切分：

1. `MVP2-EPIC-01` 案件与中间文件工作台
2. `MVP2-EPIC-02` 时限监控台与提醒机制
3. `MVP2-EPIC-03` 历史补录与迁移规则
4. `MVP2-EPIC-04` 查询工作集与跨模块导航
5. `MVP2-EPIC-05` 账单/收款/催款财务工作台
6. `MVP2-EPIC-06` 模板中心与快捷模块
7. `MVP2-EPIC-07` 固定经营报表与口径治理
8. `MVP2-EPIC-08` 提成迁移视图与提成工作台
9. `MVP2-EPIC-09` 人员主数据与账号映射
10. `MVP2-EPIC-10` 平台治理与输出增强

## 7. 第二轮 Discussion 建议议程

建议不要再做泛泛讨论，而是围绕以下议程做裁决：

1. 确认哪些旧能力必须保留为产品功能，哪些改为迁移说明。
2. 确认哪些对象不再保留旧名称和旧模型，只提供映射视图。
3. 确认哪些内容属于平台/运维史诗，而不是业务模块范围。
4. 确认管理层固定报表口径，以免后续财务口径反复。
5. 确认模板体系的边界：
   - MVP2 是否只做模板中心和常规输出
   - 高级 Word 能力是否后移
6. 确认提成域的过渡方案：
   - 是否接受不恢复“代理人结账单”对象
   - 是否必须增加人工调整能力

## 8. 最终建议

第二轮不要按“章”实施，而要按“迁移主题”实施。  
如果继续按章节推进，团队会反复做同类工作台、查询、模板、打印和映射说明，成本高且容易口径不一致。

MVP2 最值得优先投入的，不是把所有旧打印动作都补回来，而是先补 5 件事：

- 工作台
- 查询工作集
- 历史补录
- 财务台账
- 新旧口径映射

这 5 件事一旦完成，老用户迁移阻力会下降最多，且不会把系统拉回桌面时代的耦合设计。
