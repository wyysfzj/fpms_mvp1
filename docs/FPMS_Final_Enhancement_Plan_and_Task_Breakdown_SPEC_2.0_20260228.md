# FPMS Final Enhancement Plan and Task Breakdown (SPEC 2.0)

## 1. Executive Summary
- 覆盖范围：仅处理 `docs/FPMS_Code_Review_Report_SPEC_2.0_20260227.md` 中 `Partially Implemented` 的 57 条 US/FR；`Missing/Fully Implemented/Not Applicable` 条目不纳入本轮。
- 强约束：`document generation` 相关能力（导出、打印、模板文档/通知函生成）全部排除；涉及这些内容的条目仅修复其非文档生成子能力。
- 估算总工作量：约 **228 人时**（Backend 126h + Frontend 72h + QA 30h）。
- 目标符合度：本计划按“**SPEC 2.0 非文档生成范围**”执行，完成后可将当前 57 条 `Partially Implemented` 收敛到可验收的 `Fully Implemented`（以本文件 Section 7 验收步骤为准）。
- 执行步骤纪要（按要求顺序）：
  1. 从审查报告 Functional Compliance Matrix 提取 57 条 `Partially Implemented`。
  2. 对每条映射前端增强设计、后端增强设计、具体改动文件。
  3. 形成整体 Final Enhancement Plan（工时/依赖/风险）。
  4. 给出 Jira 风格任务拆解与可追踪矩阵。

## 3. Overall Enhancement Design
### 3.1 统一设计原则
- 仅做增量增强：不触碰 `Missing/Fully Implemented/Not Applicable` 条目，不做无关重构。
- 非文档生成边界：只实现“数据链路、状态链路、查询链路”，不实现导出/打印/模板文档生成。
- API 语义统一：
  - `201` 必回创建实体/标识。
  - `204` 不返回 body。
  - 错误语义固定：`400/401/403/404/409/422`。
- 权限注入统一：`_perm: None = Depends(require_perm("Title.Action"))`。
- SQLite 兼容优先：避免方言特性，保持短事务，避免依赖 RETURNING。

### 3.2 Backend 统一改动面
- Case 域：强化组合校验、参与方回填、状态联动与扩展字段规则映射。
- Document 域：强化模板默认值、回复时限任务联动、查询能力；不做文档输出。
- Task 域：强化模板规则、自动生成来源覆盖、手工维护（含删除）与今日提醒聚合。
- Fee/Annuity 域：强化计算矩阵、官费清单/缴费状态、年费任务指示链路、费用双表查询；费用草单需补齐草单头字段、明细行级录入、GOV 费率约束与金额汇总可见性。
- Billing/Collections 域：强化手工账单 AR/AP、坏账/催款、预收款扣减闭环。
- Commission/Consulting 域：强化提成自动生成、S1/S2 结算规则、顾问检索项目属性与结算纳管。

### 3.3 Frontend 统一改动面
- 统一“高级筛选 + 状态标签 + 业务来源追踪”的列表体验。
- 统一“提交前校验 + 字段级报错定位 + 保存后联动结果回显”的表单体验。
- 统一 dashboard/today reminder 与任务模块的提醒口径，并补齐今日提醒页面的导航可达性。
- 统一 API types 与页面字段（避免“后端已返回但前端未建模”的信息丢失）。

### 3.4 风险与缓解
- 风险 R1：部分条目包含文档生成子要求，与本轮排除约束冲突。缓解：在每条需求上显式标注“非文档生成子范围验收”。
- 风险 R2：多模块联动（Documents→Tasks→Fees）易出现幂等/重复创建问题。缓解：服务层幂等键与重复提交保护。
- 风险 R3：列表查询增强带来性能压力。缓解：分页默认值、索引友好过滤条件、必要时延迟加载。
- 风险 R4：前后端并行导致契约漂移。缓解：先冻结 API 字段契约，再执行页面改造。
