## Frozen Command, Result, and Transition Contract

The service exports frozen keyword-only dataclasses and operations with these exact shapes:

```python
RegisterWorkbookInputCommand(
    template_version, template_storage_path, expected_template_hash,
    upload_proof_storage_path, expected_upload_proof_hash,
    effective_from, effective_to, source_classification,
    actor_id, idempotency_key, runtime_profile,
)
ValidateWorkbookInputCommand(version_id, actor_id)
ReviewWorkbookInputCommand(version_id, decision, reason, actor_id)
ActivateWorkbookInputCommand(version_id, actor_id, at, idempotency_key, runtime_profile)
RetireWorkbookInputCommand(version_id, reason, actor_id, at, idempotency_key)
ResolveWorkbookInputCommand(at, runtime_profile)

register_workbook_input(transaction, command) -> WorkbookInputResult
validate_workbook_input(transaction, command) -> WorkbookInputResult
review_workbook_input(transaction, command) -> WorkbookInputResult
activate_workbook_input(transaction, command) -> WorkbookInputResult
retire_workbook_input(transaction, command) -> WorkbookInputResult
resolve_workbook_input(transaction, command) -> WorkbookInputResult
```

`runtime_profile` is trusted server configuration; only exact `test` is an isolated test profile.
It is never request JSON. Validation and review timestamps are generated by the service clock;
activate, retire, and resolve timestamps are server-supplied naive UTC values. The immutable result
contains only persisted server state plus `CREATED|REUSED|UPDATED|RESOLVED` disposition; it never
echoes an unverified expected hash or derives acceptance, payment, ticket, PayList, or legal facts.

Registration requires `scope_key=GLOBAL` implicitly, `PRODUCTION|TEST_ONLY`, a nonempty version,
two readable regular managed files, exact lower-case SHA-256 expectations, and a valid half-open
effective interval. It streams both files, compares their hashes, calls row 214 validation, stores
the delimiter-safe canonical structure JSON and its SHA-256, and creates `DRAFT + INACTIVE`.
`TEST_ONLY` registration is accepted only when `runtime_profile == "test"`. Replay by registration
idempotency key is `REUSED` only when every immutable command value, recomputed file hash, canonical
snapshot/hash, actor, and initial state agree; otherwise it is a conflict.

Validation re-reads and re-hashes both files, reruns row 214, and changes only exact `DRAFT` to
`VALIDATED`. Review changes only exact `VALIDATED` to `APPROVED|REJECTED`; input decision is exact
`APPROVE|REJECT`, reason is nonempty, and the reviewer must differ from the uploader. Validation and
review exact-state replay is `REUSED`; any different terminal tuple or stale predecessor conflicts.

Activation requires exact `PRODUCTION + APPROVED + INACTIVE`, an effective `at`, matching the
version's registration idempotency key, and current file/snapshot integrity. It rejects TEST_ONLY
in every runtime profile. With no current row it activates directly. With one different current
row it atomically retires that row and records it as `supersedes_version_id`; zero-or-one current
identity and exact predecessor state are mandatory. Exact active-state replay is `REUSED`; a
different actor/time/key conflicts. Retirement requires the exact current ACTIVE row, nonempty
reason, effective server time, and matching registration idempotency key; exact retired-state replay
is `REUSED` and every other stale state conflicts.

Resolution is read-only. In exact `test`, it returns exactly one effective
`TEST_ONLY + APPROVED + INACTIVE` row with no current identity. Every other profile returns exactly
one effective `PRODUCTION + APPROVED + ACTIVE + current_identity_key=GLOBAL` row. In both cases the
stored workflow/activation tuples, managed files, hashes, canonical snapshot, and interval must
still agree. Missing, ambiguous, stale, malformed, or corrupt configuration raises
`PAYMENT_WORKBOOK_INPUT_CONFIG_REQUIRED` with HTTP 409 semantics.

Invalid command shape raises `PAYMENT_WORKBOOK_INPUT_INVALID` with HTTP 400 semantics. State,
identity, replay, predecessor, file, hash, structure, and effective-time conflicts raise
`PAYMENT_WORKBOOK_INPUT_CONFLICT` with HTTP 409 semantics. Every operation validates before mutation
where possible, calls `flush()` only after a successful write transition, and never calls
`commit()` or `rollback()`; the caller owns the transaction.
