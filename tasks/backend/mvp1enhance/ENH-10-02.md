# ENH-10-02 — Create a Baseline Alembic Migration (Comprehensive Initial Schema)

**Category**: Cross-Cutting Enhancements → Database  
**Source**: `mvp1_backend_review_report.md` §6.2 Database (Item 10.1)  
**Priority**: P0  
**Effort**: M

## Goal

Create a **baseline Alembic migration** that can bring a **brand-new / empty** database to a working MVP1 schema.

Key requirement: the migration must be **safe to apply in a repo that already has tables** (e.g., your local dev DB), by using **“create-if-missing”** logic to avoid `table already exists` failures.

## Scope

### In-Scope
- Create exactly **one** new Alembic revision file that:
  - Creates **all MVP1 tables currently defined in the repo** (based on current SQLAlchemy models and the schema spec).
  - Uses **idempotent checks** (`inspect(bind).has_table(...)`) to skip creating tables that already exist.

### Out-of-Scope
- Editing any model definitions (`models.py`) or adding relationships.
- Editing Alembic config/env settings.
- Adding indexes / foreign keys (handled by ENH-10-03 / ENH-10-04).

## Hard Rules (AI‑EOS)

- Create **only one** new file (allowlisted below).
- Do not modify any other files.
- If you cannot determine the correct schema without touching other files → **STOP**.

## Allowed Files (Strict Allowlist)

- `backend/alembic/versions/enh_10_02_mvp1_baseline_schema.py` (new file)

## Required Behavior

### 1) Alembic metadata
- Set a **unique** `revision` string.
- Set `down_revision` to:
  - The **current Alembic head** revision in this repo (preferred), OR
  - `None` if this repo has no prior migrations.
- Keep `branch_labels = None`, `depends_on = None` unless the repo already uses them.

### 2) Upgrade: “create if missing”
In `upgrade()`:

- Use SQLAlchemy inspector:
  - `bind = op.get_bind()`
  - `insp = sa.inspect(bind)`
  - `insp.has_table("t_user")` etc
- For each required table, do:
  - `if not insp.has_table("t_xxx"): op.create_table(...)`

### 3) Schema source-of-truth
The baseline migration must reflect the **current repo’s schema contracts**:

- Prefer matching the **current SQLAlchemy models** under `backend/app/modules/**/models.py`
- Cross-check with `docs/03_database_mvp1_subset.md` if present in the repo

At minimum, the migration must cover all the “core MVP1” tables that exist in the codebase today (common examples include):

- RBAC/Auth: `t_user`, `t_role`, `t_user_role`, `t_role_perm`
- Master data: `t_client`, `t_client_address`, `t_client_contact`
- Cases: `t_case`, `t_case_receipt`
- Billing: `t_bill`, `t_bill_item`, `t_payment`, `t_payment_line`, `t_offset`
- Documents/Templates: `t_document`, `t_doc_attachment`, `t_doc_template`, `t_template`, `t_letter_head`, `t_system_param`
- Tasks: `t_task`, `t_task_log`, `t_task_template`
- Fees: `t_fee_rate`, `t_fee_draft`, `t_fee_item`

### 4) Downgrade safety
Because `upgrade()` is conditional (no-op when tables already exist), `downgrade()` must be **non-destructive**.

- Implement `downgrade()` as a **no-op** with a clear comment explaining:
  - Dropping tables is unsafe because the migration may have skipped creation on an existing DB.

This is an explicit safety choice for MVP1/dev.

## Acceptance Criteria

- [ ] A new migration file exists at the allowlisted path.
- [ ] `upgrade()` can run on:
  - an empty DB (creates tables), AND
  - an existing DB (skips existing tables; no crash).
- [ ] The migration file is syntactically valid (compiles).
- [ ] `alembic upgrade head` succeeds in a normal dev flow.
