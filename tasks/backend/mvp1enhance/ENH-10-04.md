# ENH-10-04 — Add Foreign Key Constraints per MVP1 Spec

**Category**: Cross-Cutting Enhancements → Database  
**Source**: `mvp1_backend_review_report.md` §6.2 Database (Item 10.3)  
**Priority**: P1  
**Effort**: S

## Goal

Add **database-level referential integrity** by introducing foreign key constraints for key relationships, aligned to MVP1 schema.

This reduces the risk of:
- orphaned rows (e.g., tasks without a case)
- inconsistent RBAC rows (e.g., user_role pointing to missing role)

## Scope

### In-Scope
- Create a single Alembic migration that adds FK constraints **safely**, including SQLite compatibility via `batch_alter_table`.

### Out-of-Scope
- Adding new columns or changing nullability.
- Data cleanup/backfill (if existing data violates constraints, the migration will fail; fix data first).
- Application-layer validation changes.

## Hard Rules (AI‑EOS)

- Create **only one** new file (allowlisted below).
- Do not modify any other files.
- If data cleanup or model changes are required → **STOP**.

## Allowed Files (Strict Allowlist)

- `backend/alembic/versions/enh_10_04_add_foreign_keys.py` (new file)

## Required Behavior

### 1) Alembic metadata
- Unique `revision`
- `down_revision` set to current head (likely after ENH-10-03)

### 2) SQLite-safe FK creation
- Use `op.batch_alter_table("<table>")` for each table needing FKs, so the migration works on SQLite.

### 3) Constraint list source-of-truth
Derive the required FK set from:
- `docs/03_database_mvp1_subset.md` (if present), AND
- current model relationships (or at least the FK columns) in `backend/app/modules/**/models.py`

Common MVP1 examples (adapt to actual schema in repo):

RBAC:
- `t_user_role.user_id` → `t_user.id`
- `t_user_role.role_id` → `t_role.id`
- `t_role_perm.role_id` → `t_role.id`

Core business:
- `t_case_receipt.case_id` → `t_case.id`
- `t_task.case_id` → `t_case.id`
- `t_document.case_id` → `t_case.id`
- `t_bill.client_id` → `t_client.id`
- `t_bill_item.bill_id` → `t_bill.id`
- `t_payment.bill_id` → `t_bill.id` (if exists)
- `t_payment_line.payment_id` → `t_payment.id` (if exists)
- `t_offset.bill_id` / `t_offset.payment_id` as per schema (if exists)
- `t_doc_attachment.document_id` → `t_document.id` (if exists)

### 4) Idempotence guard
Because SQLite may represent FK constraint names inconsistently, implement a conservative guard:

- Use `sa.inspect(bind).get_foreign_keys("<table>")`
- Consider an FK “present” if **constrained_columns + referred_table + referred_columns** match.

Only create missing FKs.

### 5) Downgrade
Implement `downgrade()` to drop the constraints created (via `batch_alter_table(...).drop_constraint(...)`) using the exact names you created.
