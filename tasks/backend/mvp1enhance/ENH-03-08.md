# ENH-03-08 — Billing: Centralize and enforce bill status transitions (service layer)

## Context / Why
The MVP1 review report flags Billing item **3.8 “Implement bill status transitions”** as needed for correctness.
Without a centralized transition rule, different flows (bill generation, offsets, reversals) can set status inconsistently.

This task implements **one authoritative transition guard** and updates existing billing service flows to use it.

## Design references (authoritative)
- `backend/app/modules/billing/docs/bill_01_db.md` (bill status fields)
- `backend/app/modules/billing/docs/bill_02_api.md` (status semantics)
- Project error conventions (BusinessError / HTTP mapping)

If any reference conflicts, `bill_02_api.md` wins.

## Target (Atomic – FIXED)
In `billing/service.py`:
1) Implement a single status-transition validator/guard function (or method) **per spec**
2) Ensure bill generation and offset application flows route status changes through this guard

## Allowed files (Strict allowlist)

## Required change (EXACT)
### A) Transition rules
- Implement an explicit allowed-transition matrix (or equivalent) that:
  - Validates a requested transition from current_status -> next_status
  - Rejects invalid transitions deterministically (per project error convention)

### B) Integrate into existing flows
- Update existing service workflows (e.g., bill generation, offset application, offset reversal if present) so that:
  - They **do not** set status directly in scattered places
  - They call the transition guard to apply status changes
