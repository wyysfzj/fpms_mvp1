# ENH-12-05 — Documentation: error codes (BusinessError + common API errors)

## Context / Why
Review report §3.3 and §6.4 item 12.5 require documenting error codes.
FPMS uses a stable error envelope (`{"error":{code,message,details}}`) and raises BusinessError codes across modules.
This doc must be code-derived: scan `raise_business_error(...)` and any explicit `code="..."` usage.

## Target (Atomic)
- File: `docs/error_codes.md`

## Allowed files (Strict allowlist)
- `docs/error_codes.md`

## Required change (EXACT)
Create `docs/error_codes.md` with:

1) `# FPMS Error Codes`
2) `## Error envelope`
   - Show the canonical JSON envelope with fields `code`, `message`, `details`.
   - Mention typical HTTP statuses used (400/401/403/404/409/422/500).

3) `## Common cross-cutting codes`
   Include at least:
   - `AUTH_REQUIRED` (401)
   - `AUTH_INVALID` or equivalent (401) if implemented
   - `FORBIDDEN` (403) with `required_perm`
   - `VALIDATION_ERROR` (422)

4) `## BusinessError codes (table)`
A markdown table with columns:
- Code
- Typical HTTP status
- Where raised (module/file)
- When it happens
- How to fix

Rules for populating the table:
- Use **only codes that exist in repo code**.
- Derive list by scanning for `raise_business_error(` and for `BusinessError(` instantiations.
- Group codes by module (Cases / Documents / Tasks / Billing / Fees / Clients / Templates / System).

5) `## Notes for clients`
- Advise client code to branch on `error.code`, not message text.
- State `details` is for debugging and may change shape.

Formatting rules:
- Keep each code entry short and action-oriented.
- Do NOT add new error codes in code (docs-only task).

## Acceptance checklist
- [ ] Only `docs/error_codes.md` is created/modified
- [ ] Error envelope + cross-cutting codes are documented
- [ ] BusinessError table contains only real codes found in the repo
