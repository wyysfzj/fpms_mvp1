# ENH-03-06 — Billing: Offset logic + balance update + auto-update case receipts + wire POST /offsets

## Context / Why
The MVP1 review report flags Billing items:
- **3.5 Implement payment offset logic with balance update** (P0)
- **3.6 Auto-update case receipts on offset** (P1)

Offsets are the accounting “核销” mechanism. If offsets do not update bill balance and case receipts deterministically, the billing ledger becomes inconsistent.

This task also prevents the prior “follow-up” situation by wiring the endpoint to the service layer.

## Required change (EXACT)
### A) Service layer (billing/service.py)
Implement a deterministic offset application workflow **per spec**:
- Create `T_Offset` (or equivalent) linked to the appropriate `payment_line_id` and `bill_id`
- Enforce required invariants (per `bill_02_api.md`), such as:
  - Positive offset amount
  - Offset cannot exceed remaining bill balance (or per spec rules)
  - Currency/client consistency where applicable
- Update bill balance (`T_Bill.balance` or spec-equivalent)
- Auto-update `T_CaseReceipt` aggregates triggered by this offset:
  - Update the correct case(s) and fee type buckets per spec/model relationships
  - Ensure updates are transaction-safe

### B) API wiring (billing/api.py)
For endpoint `POST /offsets`:
- Enforce permission: `require_perm("Payment.Create")`
- Use request/response schema(s) from `billing/schemas.py` (no untyped `dict`)
- Call the service workflow (no direct DB logic in endpoint)
- Return HTTP **201** with response fields consistent with API doc example:
  `id, payment_line_id, bill_id, offset_amt, offset_date, is_reversed`

### C) Schemas (billing/schemas.py)
- Reuse existing billing schemas.
- If offset request/response schemas are missing, add minimal ones without breaking prior schemas.
